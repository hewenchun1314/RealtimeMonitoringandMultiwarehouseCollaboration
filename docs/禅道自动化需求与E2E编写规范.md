# 禅道自动化需求与 E2E 编写规范

版本 1.16 草案 · 适用于海能发地质工程一体化项目

提需求可以从一句话、一张截图或一次实际操作开始。以下内容是所有需求交给无人值守流程前的共同标准，适用于页面、纯后端和跨端需求。简单改动可以在一小段话里交代，复杂改动按规格展开。

## 所有需求的通用内容

| 必写项 | 应说明什么 |
| --- | --- |
| 功能归属与入口 | 属于哪个项目或模块，从哪里进入或触发。页面写实际菜单路径，纯后端写服务和业务入口。 |
| 现状与目标 | 谁或哪个系统在什么场景遇到什么问题，当前行为是什么，这次希望解决什么。 |
| 预期行为与结果 | 在什么条件下触发，系统应做什么，用户或调用方能观察到什么。涉及用户操作时写清完整的主流程。 |
| 本期范围与影响 | 本次交付哪些能力、涉及哪些对象或入口、哪些既有行为要保留，哪些内容延期。 |
| 前置条件与依赖 | 需要哪些已就绪的功能、接口、数据、角色或环境，以及缺少时影响什么。没有额外前置条件时可简记。 |
| 依据与待确认项 | 标明本次采用的业务决定及材料版本，从需求入口能定位对应章节、界面或契约。仍待决定或存在差异的事项标明受影响的范围和验收项。 |
| 验收与完成条件 | 用「给定条件 → 执行动作 → 可观察结果」定义通过。让本期规则能对应到验收项、测试入口和验收范围。 |

> 短需求示例：在「测井解释 → 成果管理 → 解释结论管理」把工具栏「导出」改成「导出所选结论」，让用户知道文件包含哪些记录。本期保留现有导出规则。验收时选中两条记录，确认按钮显示新文案，文件仅含所选两条。

## 一、按功能模块拆需求

**一个功能模块一条需求。** 同一个菜单下的「按井查询」「查看层段详情」「合并层段」「导出所选结论」分别建立需求编号、材料目录和禅道 Story。划分时看用户要完成的业务目标及可独立判定的验收结果。

**菜单级总说明串联模块。** 记录整体流程、本期模块清单、共用业务规则、交付顺序和跨模块 E2E。单条需求带齐本模块的入口、边界、主流程和验收，引用直接依赖的需求编号、所需能力、就绪条件，以及共享规则的具体版本和章节。评审和研发只需加载当前模块及这些依赖。

**模块内按三类工作展开。** 各类写清交付内容、依赖和关联的验收项（AC）。不适用的类别保留栏目并说明原因。跨端模块在同一张 Story 内由自动化按实际依赖拆分 Task。

| 模块内工作 | 写清什么 | 怎么验 |
| --- | --- | --- |
| 后端接口开发 | 所属服务，新增、修改或复用的接口，输入输出、权限、校验、错误及持久化规则。已有接口注明契约、版本和可用环境，新接口未定路径时先说明必需的输入输出和业务语义。 | 从服务入口独立验证响应、异常和持久化。 |
| 前端界面开发 | 实际项目和菜单位置、本期 UI 图、控件及默认值、主流程交互说明和各界面状态。 | 从页面入口用约定样例检查控件、交互和反馈。可按原型或样例响应定义独立验收条件。 |
| 前端接口联调 | Swagger 地址与环境、每个接口的使用位置和触发动作、请求字段与界面元素的对应关系、返回字段与界面元素的对应关系，以及错误提示和保存回读。 | 用候选前端和已核验的服务版本跑真实业务链路。 |

## 二、写需求材料

| 文件 | 用途 |
| --- | --- |
| `intent.md` | 自动化材料入口，写本模块问题、范围和入口，链接本期有效材料。 |
| `spec.md` | 写规则、交互、工作拆分和 AC。简单改动可将规则和 AC 写在 `intent.md`。 |
| `record.md` | 按需求仓库约定维护来源、修订、确认依据、状态和关联禅道条目。 |
| UI 图与交互说明 | 新增或修改界面时两项都要提供。从 `intent.md` 或 `spec.md` 链接本期确认的图和对应说明，自动化执行环境须能访问。 |
| E2E、接口契约和夹具 | 按本单提供，从入口使用相对链接引用，写清适用版本。页面用例可放规格中，步骤或数据较多时可独立写 `e2e-test-data.md`。纯后端填写服务验收。 |

### 通用要求：材料可定位、行为可追溯、交付口径一致

1. **材料定位到相关条目。** 从 `intent.md` 链接本模块用到的规格章节、共享规则、交互步骤或契约位置，并写清采用的版本。简单需求可在正文直接写明。材料分文件时，核对相对链接、图稿和测试入口能在交付环境打开，AI 只需读取与当前模块直接相关的内容。
2. **每条业务规则有明确、可观察的结果。** 写清前置状态、触发条件、必要输入和结果。涉及状态变化时，明确操作后进入哪个状态，哪些数据保留、更新或回读。对会产生不同业务结果的选项，确认本期预期。业务规则和验收项使用稳定编号或具体章节引用，方便后续定位变更。
3. **从规则能追到验收用例。** 标明每项要看的是输出数据、状态变化、页面表现、接口结果或跨系统回读，再选择合适的验证方式。复杂需求可用下表串起规则和用例，简单需求在对应段落注明即可。
4. **交付范围与验证范围一致。** 规格、设计、契约、AC 和测试用例采用同一个已确认的需求修订。依赖尚未就绪、当前仅可模拟或功能延期时，写清本期能验证到哪个环节、哪些结果需要后续验证。范围或行为有变更时，同步受影响的材料，并检查关键规则在各处的表述是否一致。

| 业务规则来源 | 对应交互、接口或输出 | AC 与用例 | 本期验证范围 |
| --- | --- | --- | --- |
| [规则编号或规格章节] | [流程步骤、UI 图、接口或输出位置] | [AC 编号、用例入口及可观察结果] | [必验或回归；实际链路、模拟覆盖或延期，按实际填写] |

**怎么填本期验证范围。** 「必验」「回归」用来说明测试目的。「真实链路」「模拟覆盖」「延期」用来说明本期测到哪里。实际通过、失败或待验证由测试执行后记录。

例如，规则「保存后刷新仍能读到记录」可关联保存和查询接口、`AC-001` 及 `E2E-001`。如果本期接口只支持模拟保存，当前用例核对界面反馈，真实存储和刷新回读注明补验条件。

### `intent.md` 可复制模板

按实际情况替换示例中的研发范围。项目支持两端时，自动化优先读正文中独立一行的 `研发范围：纯前端`、`研发范围：纯后端` 或 `研发范围：前后端`。缺少标记时由拆分 Agent 研判。单端项目以项目配置为准。

```markdown
# [模块需求名称]

研发范围：前后端

- 问题与目标：[哪个角色遇到什么问题，交付后能完成什么]
- 项目与入口：[平台 / 业务项目或子应用 → 完整菜单层级 → 页面、页签或控件]
- 当前行为：[现在怎么操作、看到什么]
- 本期范围：[这次交付什么，以及保留的既有行为和延期事项]
- 前置依赖：[需求编号、所需能力、就绪条件；共享规则的章节和版本]
- 本期材料索引：[链接规格、确认记录、适用的 UI 图、交互说明和契约；注明版本及相关章节]
- 待确认项：[未决问题、受影响的规则或 AC、继续所需条件，按实际填写]
- 验收与完成条件：[必验 AC、回归范围及验收对应表或用例入口]
```

**功能归属与入口是必填信息。涉及页面时要写完整菜单路径。** 用产品界面的实际名称写完整路径，同名功能跨项目时逐个列明。已有相对 URL 一并提供，路由待设计时先写目标页面及默认页签。纯后端写所属项目、服务和业务入口。新增菜单写所属项目、完整父级路径、导航位置、菜单名称、同级顺序、目标页和可见及访问角色。例如，假设在测井解释项目的左侧一级导航新增「导出记录」，需写明与「成果管理」同级且排在其后。移动或更名时列出变更前后位置及原入口的访问行为。

### 界面需求必交 UI 图与交互说明

- **UI 图说明界面长什么样。** 可提供设计稿、可访问的原型，或在现有页面截图上标注修改。图上标出所属页面或页签、改动区域、控件名称和位置，以及涉及的弹窗、提示区域或布局。局部修改可提供一张带标注的截图。存在不同布局的关键状态时，补对应状态的图或标注。注明图的版本及适用范围。
- **交互说明定义操作后发生什么。** 关联到图里的具体控件，按主流程写明「前置状态 → 用户操作 → 系统反馈 → 下一步」。写清适用的按钮可用条件、默认值、校验、跳转和提示。取消、提交失败等关键分支写明用户停留在哪、数据和选择如何处理。
- **图和说明共同作为验收依据。** 多张图可编号，在交互步骤或 AC 中引用图号和控件名称。图与文字有差异时，确认采用的规则并同步材料后再交付。

### `spec.md` 写清行为、规则及验收条件

- **主流程按步骤写。** 从进入功能到完成业务目标，每一步写「用户做什么 → 系统怎么响应 → 接下来能做什么」。说明控件名称、输入、反馈和可用状态。弹窗、跳转或保存写清操作后的落点，以及原输入、选择和数据如何处理。取消、校验失败、提交失败等影响结果的分支写在对应步骤下。
- **数据页面写三种状态。** 有数据时，明确显示的字段、条数、默认选择和可用操作。空数据时，明确保留哪些页面元素、空态出现的位置及文案，区分适用的「未选择」和「查询无结果」。失败时，明确提示位置和内容、旧数据和输入如何处理、哪些操作可用、重试后如何恢复。异步操作涉及等待时也写明等待中的状态。
- **按场景补业务规则。** 查询或计算补数据来源、范围、单位、精度和缺失值口径。写入补保存位置、重复提交、失败后的数据和回读。视觉要求给对照和适用状态，性能要求给测量场景、数据量和通过阈值。
- **为本期行为编号。** 用稳定的 `AC-xxx` 写「给定条件 → 执行动作 → 可观察结果」，标注必验项和回归范围。三类工作和正式用例引用对应 AC。待确认的业务决定注明影响的 AC 和继续所需条件，AI 可先整理规格和用例草案，按已确认内容继续可独立开展的工作。[规格模板](../req-demo/templates/spec.md) · [公共开发交付规范](../req-demo/context/AI开发交付规范.md)

规格可以按这组栏目展开，保留适用项。

```markdown
## 主流程与关键分支
[对应 UI 图或控件 / 步骤号 / 前置状态 / 用户动作 / 系统反馈 / 下一步]

## 业务规则与页面状态
[数据、权限、写入与回读；有数据、空数据、失败时的界面表现，按适用场景填写]

## 三类工作
- 后端接口开发：[工作、契约、依赖、AC]
- 前端界面开发：[工作、设计依据、依赖、AC]
- 前端接口联调：[Swagger 地址及环境、逐接口的使用位置和触发动作、入参与返回字段映射、AC 和 E2E]

## 验收
[AC 编号 / 必验或回归 / 给定条件 / 执行动作 / 可观察结果]
```

### 前端接口联调逐接口填写

1. **Swagger 地址。** 提供联调环境可访问的 Swagger 文档地址或 OpenAPI 文档地址，注明所属服务和环境。从文档中用 HTTP 方法和路径或已知的 `operationId` 定位接口。联调请求使用独立网关时，也写明实际请求的基地址。地址尚待提供时，标明影响的接口和联调用例。
2. **接口用在哪里。** 对每个接口写明「项目 → 菜单 → 页面 → 页签、弹窗或控件」，以及触发时机，例如进页、选井、点击查询、保存或刷新回读。同一接口有多个用处时逐处列出，并说明各处的参数或结果处理差异。
3. **入参与界面元素逐字段对应。** 写出实际请求字段、界面元素及取值方式，例如「井选择器 → 已选井的 ID」。参数来自当前工区、案例上下文、固定值或前次响应时，明确实际来源。注明适用的默认值、未选时的传参和转换规则。
4. **返回值与界面元素逐字段对应。** 写出实际响应字段路径，以及它用在哪个表格列、总数、表单回填项、提示或控件状态。注明适用的展示格式、单位、空值和错误处理。有只用于状态判断或后续请求的字段时，写清具体用途。

每个接口先写「服务及 Swagger 地址｜HTTP 方法和路径｜使用位置及触发时机」，再填写字段映射。下表字段名仅用于演示。

| 方向 | 接口字段 | 界面元素或上下文 | 对应规则 |
| --- | --- | --- | --- |
| 请求 | `wellIds` | 结论列表左侧的井选择器 | 取已选井的 ID 列表。 |
| 请求 | `caseId` | 当前案例 | 取当前活动案例的 ID。 |
| 响应 | `data.items[].wellName` | 结论列表的「井名」列 | 每行显示对应记录的井名。 |
| 响应 | `data.total` | 列表底部的分页总条数 | 用于显示符合当前筛选条件的记录总数。 |

## 三、把 AC 写成能运行的 E2E

跨项目可复用的写法、用例模板和结果判定见 [E2E 编写与验收规范](E2E编写与验收规范.md)。

每条用例引用对应的 AC，沿用规格的主流程。涉及菜单变更时，从所属项目导航逐级点击，验菜单层级、顺序、权限和跳转。数据页面分别准备有数据、空数据和失败的用例及触发条件。纯后端按实配服务入口做独立验收，观察接口、后台任务或持久化结果。

| 用例字段 | 填写内容 |
| --- | --- |
| 入口和角色 | 项目、菜单、相对 URL（含必要参数）、页签及页面到达标志，或服务配置键及触发方式。写明环境和角色，凭据用配置引用。 |
| 数据与初始状态 | 提供可定位的工区、案例、井、曲线、数据集或目标记录，以及准备方法和初始值。分页、批量场景注明所需最小数量。 |
| 步骤与断言 | 每步写选哪条、填什么、点哪里、预期怎样变化。联调核对真实请求参数是否来自约定元素，以及响应字段是否映射到指定列、控件或提示。异步操作等待可观察的完成状态。 |
| 回读和恢复 | 写入、覆盖、归档或删除使用专用数据。核对目标、前置状态、操作结果及回读值，给出恢复步骤和复查方式。 |
| 实测证据 | 逐项保留实际运行版本、结果和相关截图、请求响应或日志，证据脱敏。 |

### E2E 用例可复制模板

模块 Story 写能单独运行的模块验收。跨多个模块的完整用户流程放在菜单级联合回归，由各模块用例关联对应的验收项。步骤统一写成「操作前检查 → 用户操作 → 操作后断言」，断言使用能看到、能读回或能比对的结果。

```markdown
## E2E-[编号] [场景名称]
- 对应 AC：[编号及必验范围]
- 运行目标：[测试环境、项目及完整菜单路径、待验版本]
- 前置条件：[角色或凭据引用、初始页面状态、必需服务与测试数据]
- 专用数据：[数据标识、初始值、准备方式和独立重跑条件]

| 步骤 | 操作前检查 | 用户操作 | 操作后断言 |
| --- | --- | --- | --- |
| 1 | [页面、数据及控件可用状态] | [点击位置、选项或输入值] | [提示、控件状态、接口字段或数据变化] |
| 2 | [上一步确认的状态] | [保存、刷新或到关联页面回查] | [结果确实写入及回读值，按场景填写] |

- 留证：[对应步骤的截图或脱敏请求响应]
- 恢复：[清理或重置步骤，及恢复后的核对项]
```

### 从全流程自测转为交付验收

- **数据选择可复现。** 优先使用固定标识或唯一名称。需要多组参数时，另列带编号的数据组合、预期结果和覆盖范围。用例结束条件以组合清单为准。所需记录缺失时，记录受影响的用例和补齐条件。
- **关键链路验证实际结果。** 以智能布井为例，计算完成要核对轨迹结果，保存后再到 DataPool「井管理 → 井数据」查找本轮生成的井，核对轨迹标记。优先记录能唯一对应本轮的井标识。新标签页和子应用等页面容器变化写在相关步骤，便于定位。
- **验收结果单独记录。** 运行后按用例记录待验版本、预期与实际、通过、失败或待验证结论及证据。必验链路的前端或后端断言失败都应记失败，环境或数据条件未满足时记待验证。返工和重试遵循工单流程，测试账号只记录凭据引用。

### 示例：曲线计算保存贯穿三类工作

以下数值和反馈仅供演示。真实工单使用已确认的业务规则、测试数据及可执行的准备入口。

**AC-001** 给专用井指定层段准备有效采样值 `10、20、30`，目标指标初始为空。计算保存后指标为 `20`，刷新回读仍为 `20`。

| 工作 | 该 AC 对应的验证 |
| --- | --- |
| 后端接口开发 | 用指定层段和样本调用计算保存能力，核对计算值为 `20`，用同一记录读回 `20`。 |
| 前端界面开发 | 验证曲线选项、指标映射、确认操作及成功和失败状态，可使用约定的样例响应。 |
| 前端接口联调 · E2E-001 | 使用实际前后端版本执行以下步骤，核对保存响应和刷新回读。 |

| E2E-001 步骤 | 用户动作 | 可观察结果 |
| --- | --- | --- |
| 进入和选记录 | 从「测井解释 → 成果管理 → 解释结论管理」进入，选专用井和结论。 | 目标记录可定位，指标初始为空。选中后可执行「曲线计算」。 |
| 配置计算 | 点击「曲线计算」，选择指定数据集及曲线并映射指标。 | 选项和映射显示正确，满足条件后可保存。 |
| 提交保存 | 点击保存并等待完成反馈。 | 提交期间防止重复提交。成功后显示提示，目标指标为 `20`。 |
| 回读与恢复 | 刷新后重新打开同一记录，留证后重置数据。 | 指标仍为 `20`。按用例恢复并复查初始状态。 |

可另设失败用例。例如，在已保存值为 `12` 的另一条测试记录提交无有效采样的曲线，按约定检查错误提示和原值回读。确认失败后的落点、选择保留及重试方式。

## 四、提交 Story 并确认可执行

1. **固定材料版本。** 使用现有目录 `req-demo/requirements/REQ-编号-简称/`。从 `intent.md` 能定位本期适用的规格、确认记录、原型、公共交付规范和验收。多版本材料写明适用范围和实际 Git 提交，并同步到自动化可读的工作区。确认缺少 `intent.md` 时，流程收尾为「待补材料」。[需求仓库说明](../req-demo/README.md) · [工单步骤](../.agents/skills/zentao-autodelivery/references/stages.md)
2. **按禅道入口提交。** Story 正文只填一行实际目录标识加尾斜杠，例如 `REQ-035-解释结论管理/`。标题、项目和指派人填写禅道原生字段，状态和指派匹配项目配置。真实迭代关联支持自动创建拆分 Task。迭代待定时，主工单可继续，Task 保留待建单。独立 `AC.md`、附件及独立 E2E 文件按实际材料提供。[Story 提交约定](../req-demo/AGENTS.md#本地技能与禅道提交) · [项目配置](../.agents/zentao-project.json)
3. **确认环境和数据。** 核对自动化能读取仓库、构建并启动候选版本、访问所需联调服务、用指定角色登录和准备数据。常用入口由项目配置提供，需求补充本单特有的环境、限制和第三方测试入口。需要真实页面验收时，确认工单启用了页面 E2E。[前端 E2E 手册](前端E2E操作手册.md) · [后端服务验收与联调](../.agents/skills/zentao-autodelivery/references/backend.md)
4. **按实际证据收尾。** 通用预检确认能自动登录、选工区并打开数据概览，业务场景可另附 Playwright 入口档案。正式验收核对候选版本，跨端用已交接的后台版本。流程按配置记录审查、验收、合回及适用的部署证据。关键用例受环境、权限或数据限制时，保留已验证结果，逐项记录待验证原因和补验条件。[E2E 阶段指引](../.agents/skills/zentao-autodelivery/references/e2e.md) · [REQ-035 入口档案](../req-demo/requirements/REQ-035-解释结论管理/assets/e2e-entry-smoke.json)
