# 禅道无人值守研发入门：一张需求如何从接单走到交付

项目里有两种 Codex 聊天。**监测聊天**由桌面定时任务唤醒，负责查禅道、排队和派单。**工单聊天**绑定一张需求，负责读材料、组织开发和测试、合回代码，再把结果反馈到原需求。两者通过同一份本地账本交接，所以即使聊天中断，也能查到这张单上次做到了哪里。

## 一张需求怎样跑起来

| 步骤 | 谁来做 | 做完后留下什么 |
| --- | --- | --- |
| 1. 提交需求 | 需求方把意图、规格和验收条件放进需求仓库，在禅道需求中登记材料目录并指派给接单账号。 | 禅道里有工单编号，需求仓库里有可以按路径找到的材料。 |
| 2. 发现和排队 | 定时任务唤醒监测聊天。聊天读取项目配置，分页查询禅道，通过 `workflow.py claim` 把扫描结果登记到账本。首次完整扫描登记历史基线，后续符合条件的新单按优先级排队，同级按发现顺序。 | 账本返回待复核的队首。当前配置接收指定账号的前端需求，同时执行一单。 |
| 3. 领取和派发 | 监测聊天重新检查队首的归属、指派人和状态。账本在同一次写入事务中核对队首和空闲名额。领取成功后，Windows 启动器创建工单聊天，监测聊天把实际聊天 ID 绑定到这张单。 | 工单有了派发编号和固定聊天。启动器恢复该聊天，由它领取执行权。即使两个监测轮次同时看到同一张单，也只有一个能占到名额。 |
| 4. 拆分、实施和验证 | 评审 Agent 核对材料，拆分 Agent 确认范围及任务。各端开发 Agent 写设计和计划，在主会话核验的工作树编码、跑单测；各端测试 Agent 独立审查和验收。 | 工单留存范围来源、任务与验收条件、候选版本和测试结果。跨端先完成后端合回和接口交接，再启动前端。 |
| 5. 合回和反馈 | 工单聊天逐仓核对并合回可安全合入的候选提交，记录实际合回版本和验收结论。阶段备注、最终结果和必要附件写回原禅道需求，再读回确认。 | 账本分别记录本地收尾和禅道回执。禅道暂时不可用时保留待回写项，后续轮次可以补发。 |

桌面定时任务决定监测聊天实际何时醒来。本文整理时，工作区配置的 `monitor.interval_minutes` 为 **60 分钟**；实施记录中的 **3 分钟**是首次启用时的设置。核对实际触发频率时，查看 Codex 桌面定时任务的计划和运行历史。[当前配置](../.agents/zentao-project.json) · [首次启用记录](禅道无人值守研发实施方案.md)

## 四个 Skill 各管哪件事

当前项目默认纯前端，所有需求都仅派前端任务。其他项目可配置纯后端，或配置前后端以接收三种路线。在支持两端的项目，需求作者可在 `intent.md` 写一行 `研发范围：纯前端`、`研发范围：纯后端` 或 `研发范围：前后端`；省略时由拆分 Agent 根据材料、代码和接口判断。各端阶段、交付物与旧单续接规则见[工单步骤](../.agents/skills/zentao-autodelivery/references/stages.md)。

Skill 是一套给 Codex 阅读的操作说明，入口通常叫 `SKILL.md`，也可以附带脚本和参考资料。项目在不同场景使用不同 Skill。理解上面这条自动接单流程，从第一行开始即可。

| 项目 Skill | 使用场景 |
| --- | --- |
| [zentao-autodelivery](../.agents/skills/zentao-autodelivery/SKILL.md) | 禅道里已有需求，要自动接单和研发。它分别规定监测聊天如何派单、工单聊天如何推进，以及失败、中断和回写不明时如何处理。 |
| [zentao-work-item-create](../.agents/skills/zentao-work-item-create/SKILL.md) | 需求材料已经准备好，要创建禅道条目、指派并核对建单回执。人工创建的合格需求也可以进入监测范围。 |
| [zentao-cron-dashboard](../.agents/skills/zentao-cron-dashboard/SKILL.md) | 想看禅道中“指派给我”的条目。它负责只读采集和生成看板。 |
| [zentao-dev-task-flow](../.agents/skills/zentao-dev-task-flow/SKILL.md) | 已有一条禅道研发任务（Task），要走计划审批、用户验收、完成和指派。这条流程有自己的入口和收尾规则。 |

## 主 Skill 里的文件怎样配合

以“把队首需求交给开发”为例。聊天先从 `SKILL.md` 读到派发规则，再调用 `workflow.py` 领取名额。脚本把结果写进 SQLite，聊天据此调用 `worker.py` 启动工单会话。这里的说明、命令和数据分别保存在以下位置。

| 文件或目录 | 什么时候用，解决什么问题 |
| --- | --- |
| [SKILL.md](../.agents/skills/zentao-autodelivery/SKILL.md) 和 [references/](../.agents/skills/zentao-autodelivery/references) | 总说明告诉聊天下一步该做什么。细则按需阅读，例如 `stages.md` 写各步交付要求，`branches.md` 写分支和工作树核验，`e2e.md` 写浏览器验收环境。 |
| [workflow.py](../.agents/skills/zentao-autodelivery/scripts/workflow.py) | 聊天操作账本的统一命令入口。`claim` 登记扫描和领取，`record` 登记绑定、步骤结果、收尾及回写回执。脚本处理一次请求后退出。 |
| [claim.py](../.agents/skills/zentao-autodelivery/scripts/claim.py)、[ledger.py](../.agents/skills/zentao-autodelivery/scripts/ledger.py)、[execution.py](../.agents/skills/zentao-autodelivery/scripts/execution.py) | 三者分别负责排队与预占、数据库表与事务、执行权与阶段推进。例如某次审查失败后，由阶段处理代码根据结果和重试次数给出后续动作。 |
| [worker.py](../.agents/skills/zentao-autodelivery/scripts/worker.py) | **Windows 工单启动器**，是调用本机 Codex 命令行的 Python 脚本。首次创建会话只让它回复“就绪”，绑定后再恢复同一会话正式开工。每单有独立的锁，防止重复启动。 |
| [stage_runner.py](../.agents/skills/zentao-autodelivery/scripts/stage_runner.py) 和 [branch_check.py](../.agents/skills/zentao-autodelivery/scripts/branch_check.py) | 前者负责某一步执行的时限、受控进程和停止证据。后者核对业务仓库、目标分支和本单工作树，让测试与合回能找到对应的代码版本。 |
| [writeback.py](../.agents/skills/zentao-autodelivery/scripts/writeback.py) 和 [status_board.py](../.agents/skills/zentao-autodelivery/scripts/status_board.py) | 前者管理待回写项的领取、发送授权和回执确认，实际禅道请求由执行方发出。后者把账本数据生成可读的进度页。 |
| [tests/](../.agents/skills/zentao-autodelivery/tests) | 验证调度程序自己的行为，例如并发领取、重复登记和超时处理。工单涉及的业务功能另有对应的单测和浏览器验收。 |

## 需求、代码和结果分别到哪里找

| 想知道什么 | 去哪里看 |
| --- | --- |
| 需求方究竟要什么？ | [req-demo/requirements/](../req-demo/requirements)。每条需求有自己的目录，先读 `intent.md`，再按需读规格、验收条件和附件。 |
| 业务代码改在哪里？ | [aggregation-platform-4](../aggregation-platform-4) 是配置的前端仓库入口。[项目配置](../.agents/zentao-project.json) 将各应用映射到实际仓库和目标分支，工单按影响范围建立独立工作树。 |
| 哪张单正在跑，哪一步失败了？ | 打开本机的[工单进度页](../.local/zentao-delivery/status.html)。它的数据来自同目录的 `workflow.sqlite3`。这就是 **SQLite 账本**，一个本地数据库文件，保存队列、聊天绑定、步骤尝试和回执，无需单独启动数据库服务。 |
| 这张单的设计、测试和阻断原因在哪里？ | 查看本机的[工单归档目录](../.local/zentao-delivery/items)。账本保存工单标识和证据引用，工单目录保存设计、计划、报告等实际文件。 |
| 为什么这样设计，后来如何验收？ | [实施方案](禅道无人值守研发实施方案.md)记录设计和试单过程，[建设与应用汇总](完整的设计实现整理.md)汇总应用效果。构建镜像和发布另有 [customized-release](../customized-release/README.md) 工具。 |

## 实例：沿着需求 #33 找到交付结果

2026 年 11 月 19 日，项目用独立账本对已有禅道需求 #33 做了一次整链验收。要复核这张单，可以按下面三个问题阅读。

1. **当初要求做什么？** 禅道 #33 对应需求仓库的 REQ-021，可以从需求方的原始意图读到规格和验收条件。[需求意图](../req-demo/requirements/REQ-021-主子应用联调状态提示复测/intent.md) · [需求规格](../req-demo/requirements/REQ-021-主子应用联调状态提示复测/spec.md)
2. **实际验证了什么？** 本单涉及平台基座和 Shell Hub。审查后有两次返工，首次浏览器验收还发现验收服务缺少静态资源。补齐后，两个固定候选版本通过六组浏览器场景，目录读取使用了测试响应。[实施与验收经过](禅道无人值守研发实施方案.md) · [本机浏览器验收结果](../.local/zentao-delivery/acceptance-33/candidate-e2e/e2e.json)
3. **最终交付到哪里？** 两个候选提交合回本机目标分支，禅道逐步备注和最终备注共读回十条。回执把需求编号、验证结果和合回提交关联在一起。该次验收使用独立账本，复核时应查这份回执。[本机工单回执](../.local/zentao-delivery/items/HNF-2b9e385aaf8f0529070e/validation-receipt.json)
