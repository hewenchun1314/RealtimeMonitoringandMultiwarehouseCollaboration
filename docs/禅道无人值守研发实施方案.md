## 2. 两个命令的接口

两个命令通过标准输入接收结构化数据，通过标准输出返回结果。Skill 依据返回状态推进。阶段和队列的查询使用 SQLite 只读访问。

| 命令 | 输入 | 事务内完成的操作 | 返回 |
| --- | --- | --- | --- |
| **`claim` 领取工单** | 完整扫描结果，或带工单唯一键的最新禅道状态与指派人 | 接收扫描结果时登记基线或刷新队列，按唯一键去重。接收工单复核结果时，在同一事务核对空闲名额、队首和当前资格，再登记领取和派发请求。部分扫描保留原队列。 | 扫描入账结果和待复核队首，或实际领到的工单、派发请求编号和已有绑定。无可领工单时返回原因。 |
| **`record` 保存步骤结果** | 工单唯一键、事件标识、当前尝试编号或派发请求编号、结果及证据引用 | 登记聊天绑定、步骤开始和结束、阻断和恢复、最终结果及写回回执。步骤结果与待写回记录在同一事务落库。最终结果保存后释放名额。 | 是否接受该事件、最新阶段、后续动作及待写回项目标识。 |

`record` 使用固定事件类型表达聊天绑定、领取执行权、步骤开始和结束、阻断、恢复、收尾及写回。同一事件重复提交时返回原结果。登记步骤开始或完成时，事务内核对工单与聊天绑定、派发请求、名额归属、当前步骤和尝试编号。迟到结果只关联原尝试，当前步骤由有效尝试推进。`claim` 核对扫描批次和当前队首，较旧的扫描批次无法覆盖已入账的新批次。聊天调用、Agent 执行、Git 操作和禅道 HTTP 请求均在事务外进行。

### SQLite 保存的记录

| 记录 | 用途 |
| --- | --- |
| 工单 | 以「禅道实例＋实际项目 ID＋工单类型＋工单 ID」唯一标识，保存接单配置快照、优先级、当前阶段和最终结果。 |
| 聊天派发 | 保存领取请求、可查找的工单标记、桌面项目和聊天 ID，以及待核对、已绑定或已启动状态。记录启动凭证的有效期和执行权归属。 |
| 步骤尝试 | 保存步骤、轮次、尝试编号、起止时间、最长耗时、结果、重试次数和证据。 |
| 写回 | 分别保存阶段备注、最终备注和附件的操作标识、目标工单、待补发内容及读回回执。 |

## 3. 执行流程

### 从扫描到启动工单聊天

1. 固定监测聊天按配置唤醒，分页读取禅道需求与 Bug，精确匹配项目名称、指派账号和可接收状态。调用 `claim` 将完整扫描结果入账，返回待复核队首。首次完整扫描登记历史基线，后续工单按优先级排队，同优先级按发现顺序处理。
2. 监测聊天重新核对队首的状态与指派人，携带该工单唯一键再次调用 `claim` 正式领取。队首发生变化时复核新的队首。账本保证当前项目同时执行一单。取得派发请求后在对应桌面项目创建工单聊天，新聊天先报就绪。
3. 读回实际桌面项目归属和聊天 ID，调用 `record` 绑定，再发送带有效期的启动凭证。建聊回执不明且启动指令尚未发送时，该单转为待核对并释放预占名额。后续按原派发标记找回聊天，确认绑定且重新取得名额后才启动。
4. 工单主聊天通过 `record` 一次性领取执行权。启动回执不明时，以账本中的执行权记录对账。凭证到期而执行权从未被领取时，撤销凭证、释放名额并拒绝迟到启动。执行权已被领取时，核对原尝试，确认执行已停止或被有效隔离后再释放名额。补材料、返工和中断恢复沿原聊天和检查点执行。

### 从材料检查到合回

1. 对需求只检查配置仓库中的对应目录和 `intent.md`。Bug 直接读取禅道复现材料。记录检查或读取结果，交开发 Agent。
2. 开发 Agent 写设计和计划，列出本单涉及的应用及验收条件。工单主聊天使用 `record branch_inspect` 核对配置的仓库和目标分支，按目标提交创建工单 worktree。账本验证所有 worktree 后进入编码。开发 Agent 在已核验的工作树中完成编码和单测，交回待验版本、工作目录和单测证据。
3. 测试 Agent 先做 Code Review，再做 E2E。严重问题退回原开发 Agent 修复，复审相关代码并复验受影响的场景。普通问题记录后继续。
4. E2E 优先复用已启动的服务和已打开的业务页面。服务尚未启动时，在当前前端开发仓库对应的 worktree 启动基座。已有有效登录和已选工区直接沿用，当前无工区才选默认工区。记录实际源码工作区和版本；复用环境中能验证的场景照常执行，候选版本的验收以及合回同时核对实际加载的代码。
5. E2E 结束后，由工单主聊天核对本单候选版本与目标分支，逐仓安全合回并核验结果。记录各仓实际结果，汇总上游未解决的问题。

### 超时、重试与阻断后推进

**每个时限都是单次尝试的最长耗时，从实际开始起算。提前完成就立即进入下一步。** 材料检查 10 分钟，设计和计划各 45 分钟，分支核验 15 分钟，编码 120 分钟，单测和 Code Review 各 45 分钟，E2E 90 分钟，合回与核验默认 45 分钟。启动、登录、选工区和场景验证都计入本次 E2E。实际运行以工单配置快照为准。

首次执行后每步最多重试 **3 次**。Code Review 或 E2E 发现严重问题后，一轮修复加复验占用该阶段一次重试，修复和复验分别按各自步骤计时。重启和阶段回退沿用原次数。超时后由可验证的执行控制能力停止本次尝试及其启动的进程，确认停止后再重试。SQLite 保存截止时间和结果，运行中的停止由执行环境负责。

确认无法继续，或重试用完仍失败时，生成 `blockers.md`。需求评审确认没有需求文件时，直接以待补材料收尾；其余阻断登记本步失败原因，立即执行下一步。各阶段独立核对输入并保存实际结果，直至合回完成，最终落为已交付、待补材料、待验证或阻断。保存最终结果后释放名额并自动接下一单。材料补齐、环境恢复或出现新的待验修复版本后，原工单可从阻断处开启新一轮，受阻步骤按本轮重新计数，历史尝试继续保留。同一份恢复证据只触发一次。

### 禅道逐步回写

每步结束在对应原需求或 Bug 写一句，包含实际开始时间、结束时间和结果。失败附上原因和重试次数，主动停跑时注明停跑原因。最终备注逐项汇总成功、失败和跳过。优先上传 `blockers.md` 并读回确认，附件上传受阻时在备注中写关键摘要和协作者可访问的文件位置。

每条待写回记录使用稳定的操作标识，保留用于读回匹配的备注文本或附件标识。通过 `record` 限时领取待写回项，领取到期后原执行者失去发送权，由后续轮次接管。接管时先读回原工单，确认前次请求已结束且记录缺失才补写。结果仍不明确时保留待核对记录。用 `record` 保存确认回执。写回队列继续核对和补发，研发队列按已保存的本地结果接下一单。

| **3. 实现 Skill 接单和绑定** | 写监测入口，接入扫描、领取、建聊、归属验证和启动。工单入口能从账本读回阶段。 | 验证精确匹配、优先级、首次基线和状态变更。模拟建聊已创建但回执超时，能找回原聊天，其他工单可继续。重复或迟到的启动请求只允许一次实际执行，到期未启动的工单释放名额。 |
| **4. 用模拟步骤验证故障恢复** | 接入 Agent 阶段结果、时限、返工、阻断、跳过、收尾和禅道补发。 | 提前完成立即转入下一步。首次失败加三次重试后登记本步阻断并进入下一步，重启沿用次数，晚到结果留在原尝试。模拟缺 `intent.md`、执行中断和禅道写回超时，核对各步骤结果、`blockers.md` 和自动接下一单。检测到材料补齐时，沿原聊天开启一轮恢复，并保留历史尝试。 |
| **5. 接入真实 Git 和 E2E** | 接上 worktree、单测、Code Review、基座启动、登录和工区检查、E2E 与合回。 | 各跑一条受控前端需求和 Bug，核对测试版本和合回版本。验证启动、未登录、会话复用、已有工区和默认工区五种场景。实测目标基座的实际入口和登录页，补齐 `ready_url`。 |
| **6. 连续工单验收后启用** | 排入一条可完成工单和一条可触发阻断的工单，检查全链路，再安排正式定时接单。 | 成功单交付，阻断单逐项回写并上传附件或提供可访问的位置。分别读回需求与 Bug 下的备注和附件。模拟写回领取后进程退出，后续轮次到期接管并先读回，备注和附件保持唯一，下一单照常启动。 |

验收证据应能串起同一个工单 ID、桌面项目与聊天 ID、各步骤尝试、待验代码版本、实际基座工作区、测试工区、合回结果和禅道回执。
