# 海能发地质工程一体化禅道无人值守研发设计

本项目通过 Codex 定时聊天接收指派给配置账号的禅道需求和 Bug。每条工单由一个业务主聊天协调材料评审、开发、测试、合回及禅道回写。当前接收范围为 `frontend_only`，同一时间执行一单。

流程从接单自动推进到收尾，途中无需人工答复或确认。出现阻断时，保留已完成的结果，跳过依赖该阻断步骤的工作，完成仍可执行的步骤和结果回写。工单收尾后释放研发名额，队列自动处理下一单。

## 2. 定时接单与工单聊天

1. **扫描禅道。** 在对应桌面项目下保留一条固定监测聊天，由 Codex 定时任务每 3 分钟唤醒。分页查询需求和 Bug，按配置精确匹配禅道项目名称、指派账号和接收状态。账号区分大小写。
2. **登记和排队。** SQLite 以「禅道实例＋实际禅道项目 ID＋工单类型＋工单 ID」为唯一键。首次完整扫描登记历史基线，后续新单按禅道优先级排队，同优先级按发现顺序处理。已登记工单使用原记录。
3. **创建和绑定。** 派发前重新读取工单状态和指派人，在账本登记派发请求，再在对应桌面项目下创建业务主聊天。新聊天先报就绪。监测聊天读回真实项目归属、绑定工单和聊天 ID 后，才发送启动指令。
4. **对账和续跑。** 创建回执不明确时，工单进入待核对，按唯一工单标记查找原聊天。其他工单可继续派发，待核对的聊天在确认绑定前保持就绪。补材料、返工和中断恢复均沿原聊天和检查点继续。

账本记录工单阶段、聊天 ID、当前尝试、重试次数、最终结果、阻断原因和禅道写回回执。业务完成以阶段结果和证据为准，聊天空闲时由监测轮次核对实际进展。

## 3. 研发步骤与单次最长耗时

**所有表列时限均为每个步骤单次尝试的最长耗时，从实际开始时计。提前完成就立即进入下一步。** 排队时间单独记录。到达上限仍未完成时，结束本次尝试并登记超时。

| 步骤 | 负责人 | 单次最长耗时 | 完成条件 |
| --- | --- | ---: | --- |
| 材料评审 | 评审 Agent | 10 分钟 | 需求按登记的材料路径检查需求仓库中的对应目录和 `intent.md`，找到就通过。缺失时记录路径。Bug 读取禅道复现材料并直接交给开发 Agent。 |
| 写设计 | 开发 Agent | 45 分钟 | 写 `design.md`，说明实现方案和影响范围。 |
| 写计划 | 开发 Agent | 45 分钟 | 写 `plan.md`，明确实施步骤、准备改动的应用配置键、单测安排和可验证的验收条件。 |
| 分支核验 | 业务主聊天 | 15 分钟 | 逐个核对本单涉及的应用仓库及目标分支。从目标提交创建工单工作树，验证实际工单分支和基线，保留原检出及其改动。 |
| 编码 | 开发 Agent | 120 分钟 | 在核验通过的工单工作树中实施，记录代码版本。发现必须修改后端时，记录超出接收范围的具体原因。 |
| 单元测试 | 开发 Agent | 45 分钟 | 编写或更新相关单测，实际执行并保存结果。 |
| Code Review | 测试 Agent | 45 分钟 | 审查本次改动。严重问题由原开发 Agent 修复，再由测试 Agent 复审。普通问题记入审查结果后继续。 |
| E2E | 测试 Agent | 90 分钟 | 准备环境并从实际应用入口验证计划中的验收条件。严重问题退回原开发 Agent 修复，测试 Agent 复审相关改动并重跑受影响的场景。 |
| 合回与核验 | 业务主聊天 | 45 分钟 | 核对准备合回的版本已通过 Code Review 和 E2E，安全合回目标分支，保留用户已有改动，并核验结果。存在影响合回的阻断时，记录跳过原因并继续收尾。 |

严重问题以交付影响为准，包括核心验收条件失败、原 Bug 仍可复现和已有功能出现明显回归。测试环境受阻时保存已通过的单测和审查证据，工单收尾为「待验证」。

## 4. E2E 环境准备

1. **检查基座应用。** 应用已启动时直接复用当前服务和可用浏览器会话，优先检查已有页面和应用内导航。HTTP 辅助探测显式使用 `Accept: text/html`。无 `Accept` 或 JSON 探测的深层路由 `404` 仅作为诊断证据，入口以浏览器核验为准。应用未启动时，在 `e2e.workspace` 对应的基座工作区执行配置中的 `start_command`，等待实际前端入口可用。
2. **检查登录会话。** 配置账号已有有效会话时直接复用。未登录或会话过期时，打开 `e2e.login.path` 指定的登录页，从本机凭据读取密码并登录。当前浏览器会话是其他账号时，使用独立的测试会话。
3. **检查当前工区。** 已选中的工区直接沿用，包括新登录后平台自动恢复的工区。当前会话无工区时，从平台首页按配置 ID 选择「海能发陆上示范区工区」，确认选择生效后再进入业务菜单。
4. **执行业务场景。** 验证计划中能实际执行的场景，记录运行工作区、可追溯的代码版本、工区和结果。复用服务无法证明加载本单候选版本时，保留已做的场景验证，候选版本标记待验证。基座准备、登录、选工区和业务验证共同使用本次 E2E 的 90 分钟上限。重试从环境检查开始，已就绪的部分直接复用。

## 5. 重试、阻断和恢复

1. **按步骤计数。** 每步首次执行后最多自动重试 3 次，每次重试独立计时。账本记录尝试编号、起止时间、结果和证据。应用或机器重启后先核对原尝试状态，恢复时沿用原计数。
2. **按返工轮次计数。** Code Review 或 E2E 发现严重问题时，一轮修复加复验计为该阶段 1 次重试。修复和复验分别使用各自步骤时限。返工期间的单测、复审和复测属于同一轮，阶段回退沿用已有计数。
3. **阻断后继续收尾。** 确认无法继续，或重试用完仍失败时，登记失败步骤及原因，将依赖它的步骤逐项标记「因阻断跳过」。可以独立执行的步骤继续。缺少 `intent.md` 时直接记录待补材料并收尾，连续 E2E 失败时保留已完成的步骤结果并跳过合回。
4. **释放名额并接下一单。** 本地保存最终结果和证据后，工单以「已交付」「待补材料」「待验证」或「阻断」收尾。释放研发名额后自动处理队列中的下一单。
5. **按新证据恢复原单。** 材料补齐、相关环境健康检查确认恢复，或出现新的待验证修复版本时，原工单可重新排队。轮到该单后沿原聊天从阻断处继续，保留之前的尝试和报告。每份恢复证据只触发一次，禅道状态持续为 `active` 只用于接收范围判断。

## 6. 阻断记录与禅道回写

**每个步骤结束后，业务主聊天在对应需求或 Bug 下写一句备注，包含步骤、开始时间、结束时间和实际结果。** 失败写原因与重试次数，跳过写决策时间和上游阻断，下一步骤已实际开始时可以在同一句记录。

每条遇到阻断的工单创建独立的 `blockers.md`，记录发生步骤、时间、原因和证据、已尝试的处理、受影响的后续步骤及最终结果。后续追加修复和复验结果，保留同一工单的阻断历史。

最终备注逐项汇总「成功」「失败」「因阻断跳过」的步骤。优先将 `blockers.md` 上传为对应工单的附件并读回核验。附件上传受阻时，将关键摘要和协作者可访问的文件位置写入最终备注。

> 材料评审、设计、计划、编码、单测和 Code Review 成功。E2E 因登录环境不可用，重试 3 次后仍失败，合回因 E2E 阻断跳过。本单收尾为待验证，详见附件《blockers.md》。

阶段备注、最终备注和附件分别保存回执。写回超时时先读回禅道，确认缺失后只补对应项。禅道暂时不可用时，将待补事项保存到独立写回队列，由后续定时轮次补发。研发名额按本地收尾结果释放，下一单照常启动。

## 7. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 定时发现一条前端需求和一条前端 Bug | 各自在正确桌面项目创建唯一业务主聊天，重复扫描沿用原记录。 |
| 基座、登录和工区准备 | 复用已启动的基座、有效登录和当前工区。未登录或会话过期时打开配置的登录页。无当前工区时选择配置的默认工区，再进入菜单。 |
| 步骤提前通过或达到上限 | 提前通过立即推进。超时登记本次失败，首次执行后最多重试 3 次，重启沿用计数。 |
| E2E 严重问题三次返工仍失败 | 保留成功步骤，记录失败和跳过的步骤，生成 `blockers.md`，回写最终结果并自动接下一单。 |
| 需求或 Bug 写回超时 | 按原工单读回核对，只补缺失备注或附件。研发队列继续推进。 |
