# 禅道工单按研发范围交付的流程设计

2026-11-20 · 已确认的业务流程，供改造实现与验收使用

## 1. 项目范围与工单范围

当前项目默认**纯前端**。现有 `.agents/zentao-project.json` 已配置 `development.allowed_requirement_types = ["frontend_only"]`，只登记了需求和前端工作区。本次设计沿用该字段，后端工作区、服务映射及运行环境在项目启用后端时登记。看到本地存在 `backend/` 目录不构成启用依据。

需求作者可以在 `intent.md` 正文单独写一行，例如 `研发范围：前后端`。合法值是“纯前端”“纯后端”“前后端”。历史文档可以省略。系统先读取本单领取时的项目配置快照，再按下表决定实际路线。

| 项目模式 | 需求标记 | 实际路线 | 判定来源 |
|---|---|---|---|
| 纯前端 | 任意或缺省 | 纯前端 | 项目配置 |
| 纯后端 | 任意或缺省 | 纯后端 | 项目配置 |
| 前后端 | 纯前端 | 纯前端 | 需求标记 |
| 前后端 | 纯后端 | 纯后端 | 需求标记 |
| 前后端 | 前后端 | 后端完成交接，再走前端 | 需求标记 |
| 前后端 | 缺省 | 拆分 Agent 根据验收目标、代码和现有接口选择上述三条路线之一 | AI 研判 |

**配置表达建议。** 纯前端使用 `["frontend_only"]`，纯后端使用 `["backend_only"]`，前后端项目使用 `["frontend_only", "backend_only", "fullstack"]`，表示三类工单都可以执行。按集合解释顺序。旧配置缺少此字段时默认为纯前端；空数组、拼写错误和其他组合报告配置错误，避免误开后端。配置变化只作用于新领取工单。

原始标记、判定来源和依据随工单保存。建议忽略围栏代码块中的示例，兼容全角和半角冒号。单端配置始终优先；双端配置遇到非法值或多个相互冲突的标记时，保留原文并记录材料歧义，供修正后恢复。已选路线无法覆盖某项验收条件时，列出可独立完成的任务和受阻条件，最终汇总体现未满足项。例如纯前端项目遇到必须新增的接口，只派发可做的前端任务。

## 2. 共用入口与分工

每张工单由同一个主工单会话调度、核验分支、执行合回和收尾。拆分、开发、独立测试各有负责人。各端开发 Agent 负责本端设计、计划、编码、单测及返工；阶段进程续接或重启时，以工单内保存的文件、版本和账本记录交接上下文。

| 步骤 | 负责人 | 输入、动作和交付 |
|---|---|---|
| 需求评审 | 需求评审 Agent | 根据需求工单给出的材料路径核对需求仓库及 `intent.md`，交付路径、材料状态和评审记录。确认缺少必需文件按现行规则以“待补材料”收尾。仅缺范围标记继续拆分。Bug 保留现有详情与复现材料入口，无范围标记按同一优先级判定。 |
| 范围判定与任务拆分 | 拆分 Agent | 读取评审结果和配置快照，产出 `split.md` 和账本结构化记录。列出本单范围及来源、各端任务编号、依赖、各任务对应的业务验收条件及已知阻断。跨端工单给出初步接口约定，例如字段语义、错误行为和共同验收样例。 |
| 派发 | 主工单 Agent | 根据账本中已确定的路线，把任务清单交对应开发 Agent。跨端工单先派后端，前端任务随原工单保留。派发是主会话的调度动作。 |

例如“列表展示审批状态”，拆分时明确谁负责返回状态、谁负责渲染、用哪条记录验收。端内设计再定位代码、制定实现方案；若现有接口已经返回所需字段，应在范围研判或任务说明中注明证据。

## 3. 两端各自的阶段、负责人和交付

以下各行按顺序执行。只走一端时读取该端的一列；跨端工单先执行完整后端列，完成第 4 节的交接，再执行完整前端列。

| 步骤 | 后端负责人及交付 | 前端负责人及交付 |
|---|---|---|
| design | 后端开发 Agent 产出后端设计，细化服务、数据、接口行为和兼容要求 | 前端开发 Agent 产出前端设计，确定应用、页面、交互、接口依赖和异常处理 |
| plan | 后端开发 Agent 列出服务配置键、实施顺序、单测及服务验收用例 | 前端开发 Agent 列出应用配置键、实施顺序、单测及页面验收用例 |
| 分支核验 | 主工单 Agent 按服务核对仓库与目标分支，建立工单工作树，记录基线提交 | 主工单 Agent 对计划涉及的应用执行现有工作树和分支核验，记录基线提交 |
| 编码 | 后端开发 Agent 在已核验工作树实现任务，交付候选提交及必要的运行说明；跨端工单同步编写联调文档 | 前端开发 Agent 在已核验工作树实现任务，交付候选提交；跨端工单使用实际交接的接口 |
| 单元测试 | 后端开发 Agent 构建、运行相关单测，保存命令、结果和候选版本 | 前端开发 Agent 运行相关单测，保存命令、结果和候选版本 |
| Code Review | 后端测试 Agent 独立审查候选改动，记录版本、问题和复审结果 | 前端测试 Agent 独立审查候选改动，记录版本、问题和复审结果 |
| 功能验收 | 后端测试 Agent 从服务实际入口验证接口、后台任务或其他目标行为，记录请求与响应或等价证据；有联调文档时按文档实际调用 | 前端测试 Agent 从真实页面入口执行 E2E；跨端时使用本单两端版本，覆盖拆分时约定的业务场景，记录版本和结果 |
| 合回与核验 | 主工单 Agent 逐仓检查候选及目标分支，执行合回，读回实际提交，保存每个仓库的结果 | 主工单 Agent 按相同规则核对并合回前端候选，读回各目标分支实际提交 |

### 三条实际路线

- **纯前端**　评审 → 拆分 → 前端设计、计划 → 前端分支核验 → 编码、单测 → 前端独立审查、页面 E2E → 前端合回 → 整单收尾。全程无需后端配置或后端 Agent。
- **纯后端**　评审 → 拆分 → 后端设计、计划 → 后端分支核验 → 编码、构建、单测 → 后端独立审查、服务验收 → 后端合回 → 整单收尾。以服务实际入口完成验收，无需前端仓库、浏览器或前端交接。
- **前后端**　评审 → 拆分两端任务 → 完整后端流程并合回 → 主工单会话核验联调交接 → 完整前端流程，其中 E2E 为两端联合验收 → 前端合回 → 整单收尾。后端合回是中间状态。

## 4. 跨端交接、返工与最终结论

**交接包。** 后端开发 Agent 在本单本轮的证据目录内维护 `backend/handoff.md`。包括后端任务与候选提交、已验证的环境或本地启动方式、鉴权凭据引用、测试数据准备、实际请求与响应示例、错误场景和相对初步约定的变化。后端测试 Agent 记录实际验证版本。主会话补齐逐仓合回提交和可调用版本的验证结果，向前端派发原任务清单、联调文档和测试证据。多仓服务须覆盖所有必要仓库。

**启动前端的条件。** 后端必需任务、审查和接口验收通过，相关仓库合回已核实，前端可实际调用与本次合回内容对应的版本。主会话用版本标识与调用证据，或从对应提交启动的环境与调用证据核验。合回产生合并提交时，记录候选与最终版本的对应关系；行为有变化则重跑受影响验证。只有旧环境可用、部分仓库合回或接口验收失败时，记录依赖阻断和恢复所需证据，结束本轮，保留已完成工作。

**返工。** 本端审查或验收发现严重问题，由本端开发 Agent 修复、跑单测，本端测试 Agent 复验。联调暴露后端问题时，将复现请求交后端，修复、复验、合回、更新交接版本后，再跑受影响的前端联调；前端问题交前端返工。接口变化影响另一端任务或业务验收时，主会话交拆分 Agent 修订受影响的任务和约定，记录版本，再派发。返工继续沿用同一工单、重试上限和受控超时。

**合回与收尾。** 沿用现行逐仓安全合回规则，上游验证失败时仍可合回能安全集成的候选。需要决定业务行为的冲突交回原开发 Agent。主会话分别记录代码合回、版本验证和业务验收三个事实；部分成功时逐仓保存目标提交，恢复先读回现状。所有适用步骤与业务验收通过才记“已交付”。其余沿用“待补材料 / 待验证 / 阻断”和主动停跑语义。未选中的端无需执行或生成失败记录，因依赖阻断而未执行的必需步骤须在最终摘要说明。阶段和最终结论沿用现有原工单回写与去重机制。

## 5. 落地与验收边界

- 新单在材料评审后完成一次拆分并固化路线。上线前已领取的工单，包括重试和恢复轮次，继续按原快照、原阶段名和原回写标识运行。
- 后端按服务登记工作区、仓库、目标分支、构建、单测、启动和验收入口。具体语言、服务清单和环境在接入真实后端时填写。当前项目只需纯前端配置。
- 核心验收包括范围优先级矩阵、三条完整路线、缺文件与缺标记的区别、单端能力不足的阻断、跨端交接失败与恢复、跨端返工、逐仓部分合回，以及旧工单续接与回写去重。

实施顺序、修改位置和演练方法见[具体改造计划](../plans/2026-11-20-delivery-scope.md)。
