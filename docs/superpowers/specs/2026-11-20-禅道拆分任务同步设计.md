# 禅道拆分任务的建单、关闭与重开设计

2026 年 11 月 20 日 · 实现设计稿

由拆分 Agent 管理每个拆分项对应的禅道 Task。工单主会话继续按既有路线派发前后端工作。两者通过同一份 SQLite 账本交接，禅道响应慢时，研发仍能继续。业务规则见[已确认的需求](2026-11-20-禅道拆分任务建单与关闭需求.md)。

## 一张需求的执行过程

1. **登记拆分。** 拆分成功时，在一次本地事务里保存拆分结果、逐项登记任务、写入待建单操作。事务提交后，主会话即可派研发。跨端单同时登记两端全部 Task，研发顺序沿用后端交接后启动前端的规则。
2. **并行建单。** 工单启动器为拆分 Agent 的任务管理工作启动一个受控的同步进程。它只领取这张 Story 的 Task 操作，通过项目的禅道接入层逐项办理。主会话同时可以运行开发或测试阶段。同步进程有自己的租约和时限，不占用账本的研发阶段名额，不同时写入工单的 Codex 会话。
3. **逐项归集证据。** 开发 Agent 在计划中把任务编号关联到应用或服务及其仓库。独立测试 Agent 登记每项验收结论、用例和受验版本。主会话记录各目标分支实际合回的提交。各自继续使用现有的阶段入口登记证据。
4. **逐项关单。** 当某项任务满足 B 条件，账本写入针对该 Task 的待关闭操作。拆分 Agent 执行并读回结果。若建单回执尚未到达，账本先保存证据，绑定实际 Task ID 后继续。
5. **续接和收尾。** 正常由工单内的同步进程及时处理；工单中断或本地收尾后，监测会话在既有对账轮次中续接遗留操作。对外展示两组进度，例如“研发 3/5 项通过验收并合回，禅道 2/5 张已关闭，1 张待关闭”。需求阶段备注仍走既有回写流程。

### 同步进程从哪里被唤醒

由 `worker.py run` 在现有工单运行期间监管 Task 同步进程，与执行研发轮次的 CLI 分开持有进程句柄。同步进程通过账本查找本单已提交且到期可办理的操作；一次只处理有限批次，空闲时等待下一次账本变更或短间隔复查。主会话按原路径登记阶段结果，无需等待同步批次结束。工单退出时有界停止本轮进程并保存回执，待办仍在账本中；监测会话对已收尾工单也能按操作类型找到并补发。主动停跑沿用原规则，只核对和处理停跑前已登记的待办。

## 稳定编号和账本记录

| 记录 | 保存内容及用途 |
|---|---|
| 拆分任务 | 新表以 `(item_seq, split_task_id)` 为主键。工单已有实例、项目、类型和 Story ID。保存所属端、标题、验收条件、修订号、相关仓库、验收方式、目标状态和已核实的远端状态。实例与已绑定的禅道 Task ID 建唯一约束。 |
| 任务证据 | 引用有效的阶段尝试、返工轮次和逐项验收结果，保存该项受验的版本、有关仓库及合回回执。保留失败或部分成功阶段中可独立核验的逐项证据。 |
| 待同步操作 | 扩展现有 `writebacks` 的操作类型，支持创建、关闭、重开。创建的操作标识基于工单和稳定任务编号，跨重试、拆分修订和恢复轮次保持一致。关闭、重开另含本次状态变更序号，以容纳“关闭 → 重开 → 再关闭”。 |
| 操作回执 | 记录实例、Story、执行、Task ID、动作、发送时的账号或状态，以及禅道读回的事实。绑定 Task ID、确认操作、安排下一条动作在同一个事务内提交。凭据沿用本机引用。 |

相同业务项在修订中保留编号，新增的独立要求分配新编号。拆分修订须能指出每个原项的去向；遇到清单漏项或无法对应的旧编号，保留已有绑定并记录差异，避免误建或误关。

## 禅道操作及并发恢复

**建单。** 每次实际创建前读取原 Story 当前的指派账号及所属项目，并核实该需求关联的执行。若 Story 详情未提供执行，用项目内的执行与需求关联记录确认。归属唯一时，用该执行、Story ID 和当前账号创建 Task，描述中写明验收条件及稳定拆分标识。若未关联或有多个可能执行，记录「待建单」和原因；下次对账重新查询。先前已经创建的任务保留初始指派记录。

**查重与回执。** 可复用现有客户端的 `create_task`、`get_task`，补充按执行分页查询、关闭、重开和状态核验。把可回读的稳定标识随首次创建一起写入，建单成功后核实项目、执行、原 Story、初始指派及标识。创建结果不明时先查已绑定 ID 或按标识核对原发送目标；即使 Story 后来改派或换迭代，也应先查原请求。仅当能确认先前请求结束且目标确实缺失时才重发。无法唯一核实时保留待对账记录。须在目标实例验证标识保存、查询覆盖、关单和重开路径；既有 `finish_task` 只证明支持完成任务。

**并发与先后顺序。** 沿用 `writeback_claim → writeback_send → writeback_confirm` 的租约和一次性发送凭证，增加按拆分任务串行领取及版本校验。每次发送前复核任务绑定、最新证据及动作序号。已过期但尚未发送的关闭请求可撤销；已发出的请求先读回，再按最新有效结论安排后续动作。监测会话与工单会话使用同一个领取入口，网络访问放在数据库事务外。即使一张任务阻塞，其他任务仍可同步。处于「已完成」的 Task 继续办理关闭，只有读回「已关闭」才计入关闭数。

## 逐项判定 B 条件

| 检查 | 证据和判定 |
|---|---|
| 该项验收是否通过 | 测试回执按任务编号列出通过、失败或待验证，绑定验收条件修订和受验候选提交。后端查服务验收，前端查页面 E2E；要求联调的项必须记录同一次联合验收实际使用的前后端版本。 |
| 相关代码是否全部合回 | 从本项已核实的仓库清单逐仓确认目标分支包含相应候选提交。缺少映射或任一仓库未核实，保留具体缺项。整阶段因别的仓库失败时，仍可使用已验证的部分合回回执。 |
| 最终内容是否仍受验收覆盖 | 合回后的内容与受验候选有差异时，核实最终版本上的受影响场景复验。返工或验收条件变更后，使受影响的旧证据失效。两个条件在同一份有效版本证据上成立，才登记关闭。 |

例如纯前端任务 F1 只改页面仓，F2 同时改页面仓和主应用仓。如果两项独立验收均通过，只有页面仓成功合回，F1 可以关闭，F2 保持打开。联合验收发现已关闭的后端 B1 未满足其原验收条件时，以该失败证据安排重开原 Task；修复、独立复验并合回后再次关闭。新增业务要求另分配任务编号并创建 Task。

## 验收与回归

- **数量与并行。** 纯前端 3 项建 3 张，纯后端 4 项建 4 张，跨端 2 后端加 3 前端建 5 张。延迟禅道回执，确认研发仍能开工，跨端前端仍遵守交接顺序。
- **字段与归属。** 回读每张 Task 的 Story、项目、迭代、初始指派和编号。迭代缺失或不唯一时，研发继续；归属明确后补齐原有数量。建单前改派时取新账号。
- **关闭与返工。** 5 项中 3 项满足 B，只关闭对应 3 张。分别验证部分合回、最终版本变化、联合验收失败、重开原 ID、再次关闭及独立新要求新增第 6 张。
- **恢复。** 覆盖创建成功但响应丢失、双执行者并发领取、同步进程崩溃、已发送关闭后才到达返工证据、研发先于建单完成、本地收尾后补写。检查无重复建单，账本最终状态与实际 Task 一致。
- **兼容。** 用旧账本及已领工单快照验证迁移，回归原有三条研发路线、Story 备注、附件回写及已有 Task 工具的调用方。通过本地演练与目标实例回读分别确认调度行为和禅道实际效果。

## 禅道 22.6 实施结果

同版本隔离实例中，创建后的任务可直接关闭。重开同一任务时，接口要求正的剩余工时。适配器优先读取原任务的剩余工时，其次使用估时；两者都没有正值时，填写 0.01 小时剩余工时，同时在重开备注里说明。重开请求保留原估时和已耗工时，并使用账本中核实过的初始指派账号。

项目内任务列表以创建时的验收说明为初始记录；后续修订保留原编号，实际关单依据为有效拆分清单及版本证据。进度页、原需求的阶段备注及账本可用于复核交付结果。目标项目通过领取时的 `runtime.split_task_sync` 快照选择本流程。
