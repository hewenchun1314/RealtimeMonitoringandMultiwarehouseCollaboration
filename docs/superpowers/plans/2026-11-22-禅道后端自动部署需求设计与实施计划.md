# 禅道后端自动部署需求、设计与实施计划

**目标**　后端验收通过并合回后，禅道工单自动打镜像、推镜像、更新 Kubernetes 部署，并核验新版本。

**实现方式**　在现有 SQLite 工单账本加入 `backend.deploy` 阶段。Windows 工单启动器看到待部署阶段后，由独立发布执行器认领，调用固定的 Python 发布脚本并登记结果。发布脚本调用现有 Maven 构建入口、Docker Buildx 和 kubectl。部署目标由项目配置选择，主工单 Agent 读取账本上的发布结果以继续工单。

## 一、需求和验收标准

| 编号 | 需求及验收标准 |
|---|---|
| AC-01 适用范围 | 工单包含后端、实际涉及的服务启用部署、后端审查与独立验收均通过、所需后端仓库均成功合回后，才能启动发布。合回树与验收候选树有差异时，须先有最终版本复验。纯前端工单、未启用部署的服务和旧快照按现有流程执行。 |
| AC-02 配置目标 | 按服务配置已授权的部署目标。同一个服务可登记多套环境，每次工单使用项目配置指定的一套。领取时保存目标快照。执行前确认当前项目仍允许该目标，授权撤销时停止写入。 |
| AC-03 打镜像 | 使用实际合回的 Git SHA，在本工单的干净构建工作树打包。Smart-Geo 使用现有 Maven reactor、Dockerfile、`internalrd / x64 / smart-geo-srv` 和 `publish-version.txt` 版本规则。将该 SHA 写入镜像的 OCI revision 标签。 |
| AC-04 推镜像 | 推送已经验过架构与 SHA 的镜像，读回远端镜像摘要。同一镜像标签的检查和推送互斥。已有版本标签时核对远端镜像是否属于同一实际构建，匹配则复用，冲突则报告并停止。 |
| AC-05 更新部署 | 用摘要更新目标 Deployment 中配置的容器，更新须带前置条件，避免覆盖读回后发生的其他发布。等滚动更新完成，读回工作负载和就绪 Pod 的镜像，核对实际运行的是本次发布的镜像，再执行目标环境 HTTP 检查。 |
| AC-06 纯后端 | 自动部署核验通过后即可收尾。记录接口验收、合回、镜像发布和部署状态。 |
| AC-07 前后端 | 自动部署核验通过后进入现有联调交接，传递实际后端 SHA 和验收网关。前端 Playwright 启动前从该网关复核后端版本，验收证据包含匹配的 `backend_versions`。联调发现后端缺陷并返工时，重新验收、合回和部署新版本。 |
| AC-08 失败和恢复 | 任何一步失败均保留已完成步骤的回执，报告失败原因和可恢复位置。恢复前读回仓库或集群实际状态。部署失败或版本不可核验时，工单保留已合回的事实，部署或联合验收标记为待验证。涉及该服务且须部署的拆分 Task 保持待交付。 |
| AC-09 同目标互斥 | 同一集群、命名空间、Deployment 的工单发布互斥。纯后端持有到部署验收完成，前后端持有到相关页面验收完成或工单终止。账本恢复时核对阶段和实际镜像，旧尝试仍在运行时禁止新尝试抢占。 |
| AC-10 无人值守 | Windows 工单启动器自动启动独立发布执行器。该执行器认领阶段、运行发布脚本和提交回执，主工单 Agent 通过账本接收结果。工单使用预先配置的 Docker 和 Kubernetes 凭据，全程无需人工操作或聊天确认。日志、回执和禅道只记录脱敏事实。 |

## 二、设计

### 流程

- 纯后端工单依次完成后端审查、独立服务验收、合回、部署、HTTP 核验和收尾。
- 前后端工单在后端合回与 `handoff` 之间部署。交接成功后前端按现有流程完成开发和验收。若配置关闭页面 E2E，仍须完成后端部署核验，按现有口径记录页面验收跳过。
- 跨端页面验收使用一个基座网关。多服务工单核对该网关能路由到所有须联合验收的后端版本。若服务配置了不同入口且无法从同一网关核验，联调交接报告配置冲突。
- `backend.deploy` 是一个账本阶段，内部保存打包、推送、更新和运行核验的独立回执。Windows 工单启动器负责驱动，发布执行器复用 `stage_runner.py` 的尝试 ID、超时和结束证据。
- 在拆分时按快照生成部署阶段，在后端计划确定实际服务后选择目标。项目开了部署但实际服务没有对应目标时，使用现有 `success` 尝试结果并附跳过证据推进账本，收尾显示「未配置部署目标」。有部署目标的服务以计划和合回回执中的服务键为准。

### 执行职责与交接

| 角色 | 职责 |
|---|---|
| 主工单 Agent | 照常完成后端合回和版本登记。当账本返回发布阶段时结束当前轮次，把后续动作交给启动器。恢复轮次从账本读部署结果，再接着做联调交接或收尾。 |
| Windows 工单启动器 `worker.py` | 工单启动、恢复或 Agent 轮次退出时，检查账本的实际可执行阶段。遇到 `backend.deploy`，自动运行发布执行器。部署状态已入账后，按下一阶段恢复同一个工单会话。 |
| 发布执行器 `backend_deploy_runner.py` | 通过账本原子认领待部署阶段，核对工单轮次、服务、合回版本和授权目标，调用阶段运行器启动固定发布脚本。自动登记成功、跳过、失败或超时，交由账本决定重试或后续阶段。 |
| 发布脚本 `backend_deploy.py` | 按受控输入完成打包、推送、更新部署和 HTTP 核验，保存供账本验证的分步回执。 |

启动器依据账本阶段分派，不依赖 Agent 在聊天中发出的命令。Agent 轮次结束或安全停止后才启动部署。部署过程中执行器中断时，先确认上一尝试已结束并读回外部状态，再决定续跑。正常部署和页面验收返工中的重新部署均由同一入口识别。现有 Task 同步器可作为后台执行和回执处理的结构参考。

### 配置

配置放在 `.agents/zentao-project.json` 的 `development.backend_bundle.services.<服务键>.deployment` 下。下表是首版拟定字段和试点状态。

| 字段 | 用途 | Smart-Geo 试点 |
|---|---|---|
| `enabled` | 显式启用自动发布 | 初始为 `false`，实测后经项目授权开启 |
| `target`、`targets` | 项目选择的目标键及目标配置映射 | 可登记 `internalrd-test` 候选，实际环境用途待确认 |
| `registry`、`image_repository`、`platform` | 镜像地址与架构 | `hzhub.tracyenergy.cn:6443`、`internalrd/smart-geo-srv`、`linux/amd64` |
| `cluster_id`、`kube_context`、`namespace`、`deployment`、`container` | 集群连接和唯一部署目标。上下文别名共享同一实际集群 ID | Rancher 集群 ID 为 `c-m-wh2j6p2w`，候选 `internalrd/smart-geo-new`，本机 context 和容器名待核实 |
| `gateway_url`、`verification_path` | 真实 HTTP 核验入口及版本核验路径 | 候选网关 `http://10.10.4.140:31111/`。已确认端口属于 `cnooced-gateway`，上游与版本路径待核实 |
| 凭据引用 | 集群连接由 `kube_context` 指向工单账号的本机 kubeconfig，HTTP 校验可配 `http_credential_ref`，镜像推送使用工单账号的 Docker 凭据存储 | 部署账号及目标访问权限待配 |
| `build_dependencies` | 从配置固定 Maven reactor 依赖仓库的 Git SHA | 启用前填写通过验收的 `tet-common-java` 提交 |

服务未配置部署时继续原流程。启用的目标必须通过配置校验。工单正文和需求材料可以说明验收环境，脚本使用项目授权的目标配置执行。当前项目的前后端派发开关由项目负责人按原约定单独启用。

### 发布执行

1. 读取验收与合回回执，核对服务、提交及项目当前授权。只读检查 Docker、集群 context、容器和目标更新权限。用本单已确认的构建依赖和实际合回的检出版本调用后端构建命令。按现有打包规则以仓库提交数和 `srv-workspace/publish-version.txt` 计算版本。使用只含运行时 JAR 与必要 Dockerfile 文件的临时上下文执行 Buildx，构建参数 `VCS_REF` 使用实际合回 SHA。确认镜像架构与 revision 后保存本地镜像标识。
2. 推送前按镜像仓库、镜像名和标签取得账本排他占用，记录预期标签和本地镜像配置摘要，再读取远端标签。同轮重试按已记录摘要比对，历史标签缺少回执时须能核实 revision、架构及镜像身份才能复用。标签匹配时跳过推送。仓库启用标签不可变可以约束账本以外的发布者。推送成功后记录远端摘要及平台镜像摘要关系，释放标签占用，用 `<registry>/<repository>@sha256:<digest>` 作为部署引用。尝试中断时先确认执行结束并读回远端标签，再决定是否重新推送。
3. 对目标工作负载获取账本排他占用，读回并保存原镜像和预期部署引用。使用显式 context、命名空间、Deployment 和容器更新镜像。通过带读取时容器镜像前置条件的 Kubernetes 补丁执行更新，冲突后重新读回并记录原因。用带超时的 `kubectl rollout status` 等待，读回 Deployment 期望镜像、更新后的就绪副本及新 Pod 实际 imageID。Buildx 若输出索引摘要，按已记录的架构对应关系校验 Pod 使用的平台摘要。
4. 走配置的真实 HTTP 入口验证。纯后端至少验证健康及关键只读接口，并结合 Pod 镜像确认版本。跨端网关应能读回当前服务 SHA，或提供等价的确定性请求证据。Smart-Geo 已可在镜像标签写入 SHA，HTTP 版本读取方式需要在试点中核实，必要时增加受控版本字段。仅凭 HTTP 200、健康检查或鉴权错误，不能确认该网关已访问本单部署。
5. 按服务写入发布回执。至少包含服务键、实际合回 SHA、完整镜像标签和摘要、目标、原镜像、新 Pod 核验、HTTP 结果及失败阶段。更新超时或回执缺失时先读回实际版本。目标已使用期望摘要时续跑核验，远端已有匹配摘要时从更新部署续跑。发现目标镜像已被其他发布改动时停止写入并记录冲突。

打包、镜像推送和运行部署分别记账。多服务工单在更新任何目标前，通过一次账本事务取得本单所需的全部部署占用，再逐服务处理。失败回执中保留已经发布的服务。试点失败后保留旧镜像信息供回退处理，本阶段的首版验收以准确报错和可续跑为准。

### 现状与启用条件

- 本机已安装 kubectl，查询默认配置未发现可用 context。正式启用要以**工单运行账号**核对 Docker 镜像仓库访问、Kubernetes 目标权限和 HTTP 核验入口。
- Rancher 上看到了 `internalrd/smart-geo-new` 和 `smart-geo-srv:1.3.23`，也核对了 `cnooced-gateway` 的 NodePort 是 `31111`。核对网关上游、容器名以及该环境可用于无人值守验收后，再开放自动更新。
- Smart-Geo 当前工程配置暴露 Actuator Info，源码中尚无生成提交信息的配置。试点须确认可经验收入口读到完整提交 SHA，并在模板中填写实际版本路径。默认探针读取 JSON 的 `git.commit.id`，也支持项目指定该字段的位置。
- 首版以一个 Smart-Geo 测试目标验证全链路。离线回归使用临时 Git 仓库、临时 SQLite 账本和模拟 Docker、kubectl、HTTP，真实试点单独用已授权的目标验证。
