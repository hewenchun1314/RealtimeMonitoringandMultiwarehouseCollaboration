# 禅道自动接单前端验收改造计划

**目标**　前端先合回，再从主工作区通过 AgentLimb 验收。功能失败进入返工和复测，E2E 最终结束后按配置推送和部署。

**实现位置**　项目的禅道自动交付脚本、账本、配置、运行说明和现有测试。使用 Python、Node.js、SQLite、Windows 阶段运行器和已配对的 Chrome。

## 最终流程

```text
工单工作树开发、单测、代码审查
    → 等待交付资源
    → 本地合回目标分支
    → 主工作区执行 E2E
        → 功能问题：开发 Agent 修复、单测、复审、提交，测试 Agent 用新版本重跑 E2E
        → 环境问题：恢复启动或登录等前置条件，再重试；到时限后记录受阻
    → 本轮 E2E 所有用例有最终结果，返工与复测结束
    → 按配置推送、部署并分别读回结果
    → 完成收尾，释放资源
```

E2E 最终通过、失败或受阻都可以进入发布阶段。正在验收、返工或等待复测的工单继续等待。合回、Git 推送、部署各自保留版本、授权和实际结果校验。跨端工单继续使用其后端联调交接确定网关和服务版本。本计划调整前端合回、E2E 和前端发布顺序。

## 1. 改流程和多工单排队

- [ ] 修改 `delivery_scope.py` 的前端路线，把 `frontend.integration` 放在 `frontend.e2e` 前。未启用 E2E 的工单按配置跳过该阶段。将新规则写入新工单的路线快照，让进行中的旧工单按已记录的阶段恢复。旧路线仍按共享资源排队，最迟从首次占用主工作区或验收端口前取得占用。启用新路线前对账现有活动尝试。
- [ ] 从进入合回前开始，通过 SQLite 事务按主工作区、目标 Git 分支和共用前端端口登记交付占用。占用覆盖 E2E、主工作区返工、复测、推送、部署和结果登记。资源冲突的工单在合回前等待，各自的接单、开发、单测和代码审查可以继续。
- [ ] 把占用关联到工单与实际运行回执。工单中断时先对账 Git 结果、阶段运行器和 Windows 进程停止状态，再由原工单恢复或收尾。共享资源仍由旧工单使用时，下一单继续等。
- [ ] 修改 `route_execution.py` 和 `execution.py`，在同一工单内保存初次验收、返工与最终验收版本。调整当前 E2E 结束时释放现有锁的逻辑，交付占用一直保留到发布收尾。

## 2. 从主工作区启动并复用 Chrome

- [ ] 修改 `agentlimb_e2e.py`，正式验收从成功合回回执取得各应用的实际 SHA。按项目配置定位主工作区中的基座和子应用，核对启动所涉及的仓库路径、SHA 及会影响页面的本地改动。启动前、业务场景前和结束时核对版本。合回后的前端启动使用这些现有目录和依赖。
- [ ] 在 `.agents/zentao-project.json` 登记 `start_command` 对应的完整本机前端端口清单，和页面必须就绪的端口。接单前诊断端口、前端启动端口和镜像发布端口各按实际用途读取。接单预检如需启动服务，也先核对正式验收的共享端口占用。验证配置中的启动命令：

  ```powershell
  npm run serve-shell-hub --gateway=http://10.10.4.140:31111/
  ```

- [ ] 在 `worker.py` 接入正式 E2E 的宿主交接、尝试绑定和结果读回，沿用 Windows 阶段运行器记录进程和超时。端口空闲时从主工作区执行配置命令。已有服务时先验证页面实际加载的资源是否对应本轮验收版本。验证通过就复用，版本旧或无法核对则走重启。
- [ ] 专用电脑允许自动回收验收所需端口。对配置端口查询监听进程，核对 PID 和进程身份，停止占用进程并复查端口。所有所需端口释放后启动。记录实际占用端口、退出情况、启动日志及超时。验收所用进程按受控运行记录管理。
- [ ] 修改 `agentlimb_e2e.cjs`，连接已经打开并配对的 Chrome，复用同一浏览器配置的登录状态，使用本次测试标签页。可信资源指纹由已核对的本地版本或其产物生成。打开页面后核对每个受影响应用在本次页面加载时拿到的资源身份或响应正文。可用内容指纹化的资源 URL 与页面执行标记关联到同次加载。另发请求的响应只提供诊断，证据采用本次加载结果，防止旧进程、缓存或错误微应用入口导致验到别的版本。
- [ ] 回执记录工单、尝试、各仓实际 SHA、资源指纹、前端复用或重启情况、业务用例结果。Chrome 配对或登录异常记为环境受阻。

## 3. 功能失败在主工作区返工

- [ ] 基于已确认版本的业务断言失败，记录复现步骤、预期、实际和证据，交给对应的开发 Agent。独立用例继续执行。前端返工从已合回的主工作区修改，沿现有宿主 Git 入口提交本单文件，保留钩子、原文件状态和提交回执。
- [ ] 修改 `development_git.py` 及宿主 Git 执行逻辑，支持本单持有交付占用时在指定主工作区返工。登记修改前的目标 SHA 和文件基线。遇到同一文件已有其他未提交修改或目标 SHA 变动时先协调或对账，保护现有改动。
- [ ] 返工后执行单测和复审。用同一账本事务更新有效合回版本回执，将旧版本的 E2E 与远端推送证据标记为历史。E2E、推送和部署统一读取更新后的目标 SHA，再以新版本重新验证本轮 E2E。开发提交成功时显示「已修复，待复测」。复测通过后显示最终的通过结论。首轮失败和历次测试保留在历史里。
- [ ] 启动、端口、登录、资源版本或测试数据异常走环境恢复。使用账本已有的阶段超时和重试上限。达到上限后记录每项最终结果及未执行原因，结束本轮验收，让发布与下一单继续。返工提交未完成时保存本单修改和停止证据，保持最后一次成功提交的 SHA 为可核对版本。发布准备需校验工作区与发布输入一致，工作区整理受阻则如实记录发布阻断。

## 4. 发布和禅道记录

- [ ] 修改 `route_evidence.py` 的推送资格和 `deploy_control.py` 的前端发布判断。E2E 条件取最新版本的**终态**，成功、失败或受阻均可通过时间顺序校验。E2E 或返工仍在进行时发布保持等待。
- [ ] 发布仅使用本单最终的目标 SHA。继续核对实际合回回执、目标分支、Git 远端回执和部署目标，保留构建和发布自身的失败结果。
- [ ] 更新 `task_evidence.py` 和工单收尾说明，分别记录 E2E、Git 推送和部署的实际结果。最终 E2E 通过时用通过作当前结论。最终存在失败或未验项时保留这些项目及原因，发布成功仍按实际记录。
- [ ] 更新技能内的 E2E、工单阶段和宿主运行指引。Bug 2、Bug 4 实机验收沿原工单按账本恢复，登记实际待验 SHA、各项用例结果和本轮证据。

## 验证清单

- [ ] 路线测试覆盖纯前端、跨端、关闭 E2E、旧路线快照，以及首次失败后最终复测通过。
- [ ] 发布门禁测试覆盖进行中或待复测时等待，最终失败或受阻后可以推送部署，最终发布 SHA 为复测版本，以及推送或部署自身失败如实记录。
- [ ] 启动测试覆盖端口空闲、同版复用、旧版重启、其他进程占用配置端口、释放失败、启动失败及资源指纹不匹配，覆盖同一 URL 下页面仍运行旧资源、另发请求已经返回新资源的情况。
- [ ] 多单测试覆盖 A 持有资源时 B 可以开发且在合回前排队，A 收尾释放后 B 能继续，以及异常退出后的恢复不会重复提交或误放行。
- [ ] 浏览器测试覆盖复用已有 Chrome，校验实际资源，业务断言失败触发返工，环境阻断按原阶段重试，最终回执显示实际结果。主会话预检用 worker.py 的 e2e-preflight 命令检查浏览器可达性，正式验收通过由本轮工单回执确认。
- [ ] 回归现有 Python 和 Node.js 测试。在项目根目录运行：

  ```powershell
  python -B -m unittest discover -s .agents/skills/zentao-autodelivery/tests -p "test_*.py"
  node --test .agents/skills/zentao-autodelivery/tests/test_agentlimb_e2e.cjs
  ```

- [ ] 在专用电脑上至少跑通一次真实工单，读回一条与合回 SHA 对应的正式 AgentLimb E2E 回执。Bug 2 优先验证重复提示和选井流程。Bug 4 验证四个刷新图标和图表正常渲染。用测试环境验证最终失败仍可进入后续阶段。
