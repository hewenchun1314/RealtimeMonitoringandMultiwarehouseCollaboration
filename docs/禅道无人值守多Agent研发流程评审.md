# 禅道无人值守研发该选几个 Codex 项目

🟢 **选一个 Codex 项目。** 把需求、前端、后端、测试四个 Git 仓库放在同一个父目录，把这个父目录设为 Codex 项目。每张禅道工单开 **1 个主对话 + 5 个独立干活的对话**。

🔴 **这次舍弃“四个仓库各建一个 Codex 项目”。** 拆成四个项目后，主 Agent 每次派工还要选项目，中断后也要跨项目找回原对话。对你最关心的“前后端同时开发”和“测试必须独立执行”，拆项目都没有额外保证。

**最终开发效果谁更好？** 在需求、模型、独立评审和测试条件相同时，预计两种方案交付的功能质量接近。比如后端改了接口，两种方案都需要前端按同一份接口约定开发，测试 Agent 也都要用本单的前后端版本验证。

**哪种更容易中途卡住？** 对这条由一个主 Agent 全程协调的流程，四项目方案多一层跨项目派发和找回对话的工作，更容易在交接处卡住或重复派工。单项目更容易出问题的地方是选错子仓或工作副本，派工时应核对实际路径。两种方案都要保存阶段、会话 ID 和提交号，重启后才能接着做。这个判断基于流程设计，目前没有两种方案的实测中断率。

## 哪些地方各有优势

| 你关心什么                      | 哪个更好           | 原因                                                                                                 |
| ------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------- |
| AI 从接单一路做到交付           | **一个项目更省事** | 同一个主对话可以跨仓派工、收结果、安排返工，少维护一层项目对应关系。                                 |
| 开发 Agent 进入正确仓库         | **四个项目更直接** | 前端项目默认进入前端仓。用一个项目时，主 Agent 每次要写明工作目录，并核对实际路径。                  |
| 前后端能否同时干活              | **两种都行**       | 分别启动两个对话，各写自己的仓库。多张工单同时改同一仓库时，每单使用单独的工作副本（Git worktree）。 |
| 能否防止主 Agent 跳过评审或测试 | **两种都要查回执** | 要核对独立对话的运行记录和交付物。项目数量无法证明某张工单做过评审或测试。                           |
| 测试能否发现真实问题            | **两种都要查版本** | 测试 Agent 要确认运行的是本单的前后端代码。若误连旧服务，即使测试通过，也无法验收这次改动。          |

**选一个项目要承担的代价**是调度程序要管好三件事：每个 Agent 进入哪个目录、允许改哪些文件、测试时连哪个服务并使用哪份数据。两套方案在这些条件相同时，预期交付质量接近。目前没有对照运行数据证明哪套质量更高。

## 第二章　选一个 Codex 项目的优缺点

### 🟢 优点

- **评审和拆解方便。** 同一条需求涉及页面和接口时，评审 Agent 可以从同一个父目录找到需求、前端和后端代码。拆解 Agent 可以把双方要遵守的接口约定写成一份，再交给两个开发对话。
- **派工和重试少一个步骤。** 主 Agent 确定工单、角色和仓库后，就能在同一项目内派发。比如后端失败、前端已完成，主 Agent 可以保留前端提交，按工单记录找回后端对话，只重试失败的一端。

### 🔴 缺点

- **容易进错工作目录。** 两张工单都改前端时，两个对话可能写到同一份代码。派工时要给每张工单分配独立工作副本，并在动手前核对路径和分支。
- **角色之间容易越权。** 如果整个父目录都可写，开发 Agent 也能修改测试用例，导致代码和验收标准一起被改。运行环境要限制各角色能写哪些目录。
- **主 Agent 容易代做。** 主对话能看到所有材料，可能自行写一份评审结论就继续派开发。调度程序要拿到独立评审对话的完成回执和评审结果，才允许进入拆解。开发、测试同样要核对各自的对话和交付物。
- **联测容易测错版本。** 四个仓库放在一起，测试 Agent 仍可能连到上一张工单启动的后端。出测试结论前，要核对实际运行的前后端版本与本单提交号是否一致。

**取舍：建议选一个项目。** 对无人值守工单，集中派发和跨仓拆解更省事。采用这个方案的前提，是调度程序能核对工作目录、限制写权限、验证独立对话并确认实测版本。如果写权限只能按项目隔离，就选四个项目。

## 第三章　四个仓库各建一个 Codex 项目的优缺点

每个仓库各有一个项目：需求、前端、后端、测试。每张工单仍由一个主对话协调。需求评审和任务拆解可以放在需求项目，但各开一个对话。

### 🟢 优点

- **开发更容易进对仓库。** 主 Agent 把前端任务派到前端项目，前端对话默认从前端仓开始。它仍要核对工单分支，但少了一次从父目录挑仓库的机会。
- **每个角色有固定的运行设置。** 前端项目可以配页面构建命令，后端项目配服务启动命令，测试项目配联测入口。如果这些设置按项目加载，派工时只需补充本单的版本和任务。
- **有条件把开发和测试的权限分开。** 如果运行环境支持按项目限制写入，可让开发 Agent 只能改业务仓，保护测试仓里的验收用例。这个优势取决于实际权限配置。

### 🔴 缺点

- **评审和拆解需要跨项目取资料。** 例如要判断“新增字段是否已经有接口”，需求评审 Agent 还要读后端代码。调度器要提供相关仓库、读取权限和代码版本。
- **失败后多一步找回工作现场。** 后端提交后若主 Agent 重启，需要从工单记录找到后端项目、原对话和提交号。少记一个，就可能把已经做完的任务再派一次。
- **测试要把几个项目的结果对齐。** 测试项目有自己的用例，但必须拿到本单的需求版本和前后端提交号。后端修复后，还要确认联测服务已换成新版本，才能复测。

**关于并行和防跳步：** 四个项目都建好了，前后端仍要由主 Agent 分别启动才能并行，五个阶段仍要逐一核对独立会话回执和交付物。若这就是拆项目的唯一目的，保留一个项目即可。

🟡 **什么时候值得选四个？** 当你必须禁止开发 Agent 修改验收用例，而且运行环境只有按项目才能强制这项限制时，选四个。此时多做跨项目交接，换来的是测试结果更可信。

## 第四章　无人值守研发最担心的问题

### 主 Agent 会不会自己干完，再说五个 Agent 都参与了？

🔴 **最担心的是工单显示“已完成”，却查不到谁审了需求、谁写了代码、谁跑了测试。** 例如，脚本找到需求文件，只能说明材料齐全。如果这一步就算“评审通过”，需求里的矛盾可能一直留到联测。

🟢 **让调度程序逐个核对。** 启动器直接记录 Codex 返回的对话 ID。一张完整工单应当能查到五个不同的执行对话，而且每个都与主对话不同。每个阶段还要交回自己的结果：

| 独立对话 | 调度程序要收回什么                           |
| -------- | -------------------------------------------- |
| 需求评审 | 针对本版需求的疑点、验收条件和评审结论       |
| 任务拆解 | 前后端各自的任务、双方使用的同一版接口约定   |
| 前端开发 | 前端仓库中能查到的提交号和自测结果           |
| 后端开发 | 后端仓库中能查到的提交号和接口验证结果       |
| 测试     | 实际运行的前后端版本、逐项测试结果和原始记录 |

### 测试 Agent 会不会受开发 Agent 影响，把错误当成正确？

🔴 **会有这种风险。** 例如，需求写着“保存后刷新页面，修改仍然保留”。开发 Agent 汇报“点击保存后已有成功提示，自测通过”。如果测试 Agent 顺着这句话只检查提示框，即使刷新后数据丢失，它也可能误判通过。两个独立对话仍然可能犯同一个错误。

🟢 **让测试 Agent 先独立确定预期，再验证开发交付的版本。**

1. **先写预期。** 主 Agent 给测试对话传入已评审的需求和验收条件。测试 Agent 据此写下操作和预期结果，再看开发自测报告。上例要写明保存什么值、何时刷新、刷新后应读回什么值。需求有歧义时，标记待澄清。
2. **交版本，单独交判断。** 开发提供前后端提交号、启动方法和测试数据。测试对话独立启动，派测消息不复制开发对话里的“已修好”“自测通过”等结论。定位失败原因时，再查开发日志和实现。
3. **凭实测结果判定。** 测试报告逐项记录预期、实际结果和证据。若刷新后读回旧值，这项就判失败；若环境不允许刷新验证，就记待验证。开发自测报告不能代替这条记录。

**怎么验证这个设计有效？** 在测试环境准备一个会弹出“保存成功”、刷新后却丢数据的版本，让测试 Agent 按原需求验收。它应当能报出“刷新后读回旧值”，并据此判失败。这个例子比单看测试会话 ID 更能检验它是否独立判断。

**对项目选型的影响。** 一个项目也能使用独立测试对话并控制派测内容。即使拆成四个项目，只要主 Agent 仍把开发结论当成验收依据传给测试，这种误判仍可能发生。

### 还有哪些问题会让工单卡住或交付出错？

| 🔴 担心什么                                            | 🟢 自动流程应怎样处理                                                                                                            |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 说好前后端并行，实际等前端做完才派后端。               | 接口约定确定后，主 Agent 连续派发两个对话，再分别等结果。需要确认是否并行时，查两份运行记录的起止时间有没有重叠。                |
| 两张工单改到同一份前端代码。                           | 每张工单使用自己的工作副本。开发对话动手前核对工单号、仓库、分支和实际目录；发现错配就停止写入。                                 |
| 开发改了验收用例，或者测试连到旧后端，报告却显示通过。 | 用写权限保护验收用例。测试对话记录用例版本，并从实际运行的服务核对前后端版本；版本对不上就记为待验证。                           |
| 后端已提交，主 Agent 突然中断；下一次扫描又从头开发。  | 用工单号找回原主对话和本次尝试。原对话还在运行就继续等；已经提交就核对并回收结果；确认旧执行已停且任务失败后，只重试失败的一步。 |
