# 禅道自动化接入公司知识库需求与实现

禅道无人值守研发在工单材料评审通过后，通过公司知识库 MCP 查询现有平台能力、接口、组件和跨应用依赖。拆分 Agent 用查询结果确定本单与现有能力的差距，设计 Agent 用它定位实现和复用点。独立验收依据候选版本的实际运行结果登记结论。

## 需求与验收标准

| 需求 | 验收标准 |
| --- | --- |
| 材料评审 | Story 按现有流程同步需求仓库并核对 `intent.md` 等工单材料，缺失时收尾为「待补材料」。Bug 核对原单复现信息。该阶段只使用工单材料。 |
| 任务拆分 | 遇到现有能力、应用归属或跨应用依赖不明确的工单，Agent 查阅相关知识，并在 `split.md` 记录所用条目及其影响的拆分决定。范围明确的工单可直接拆分。研发范围仍按项目配置和工单材料判定。 |
| 研发设计 | 优先沿用 `split.md` 的引用。需要补充共享组件、接口或上游依赖证据时，查询相关条目，并用当前目标分支的源码或实际接口核验，在 `design.md` 记录结论和位置。 |
| 知识版本与证据 | 引用所读条目的 ID、版本和发布状态。知识描述与当前实现有差异时，记录差异及核验依据。独立验收可沿用引用补充场景，验收结果关联实际验证的候选版本。 |
| 异常处理 | 无命中或调用失败时，记录原因，继续使用工单材料、源码和实际接口。关键条件经核对仍无法确认时，按任务编号登记阻断，独立任务继续推进。 |
| 应用授权 | 使用独立的只读应用 Key，授权项目所需的知识空间。Key 由 Windows 启动环境提供，工单产物和禅道备注只记录必要的引用与结论。 |

## 实现路径

1. **工单主会话派发。** 主会话按账本的阶段、尝试编号和截止时间启动 Agent。材料评审通过后，把知识库查询规则传给拆分和设计 Agent。该接入沿用现有 `split`、`frontend.design` 和 `backend.design` 阶段以及原有账本字段。[工单执行入口](../.agents/skills/zentao-autodelivery/SKILL.md#工单执行入口)
2. **阶段 Agent 调用。** Windows `stage_runner.py` 启动受控 Codex CLI。Agent 在 `company-knowledge` 上先调用 `search_knowledge`，以功能名、业务对象或页面入口搜索。再用命中的 `itemId` 和 `versionId` 调用 `get_knowledge` 读取该版本。设计需要核对依赖或引用关系时可调用 `traverse_knowledge`。[阶段运行器](../.agents/skills/zentao-autodelivery/references/stage-runner.md) · [公司知识库 AI 接入说明](http://10.10.4.171:30015/tet/knowledge-web/ai-guide)
3. **工单证据复用。** 拆分结果写入本轮 `split.md`，设计核验写入对应端的 `design.md`。建议每条引用包含条目名称、`itemId`、`versionId`、发布状态、影响的任务或设计决定，以及适用时的源码或接口核验位置。后续阶段从本轮产物读取这些引用。[阶段查询规则](../.agents/skills/zentao-autodelivery/references/stages.md#公司知识库查询)
4. **失败归到对应任务。** 检索在当前阶段时限内完成。无结果、鉴权失败或超时，先用本地材料和实际契约补证。仍无法核实的关键前置条件按现有 `evidence.task_blockers` 记录原因和证据。[账本命令](../.agents/skills/zentao-autodelivery/references/workflow-cli.md)

## 接入配置

在公司知识库的「应用接入」页创建或编辑禅道自动化应用。负责人选实际维护人，应用保持启用，授权项目使用的知识空间，维护动作留空，应用列表正常显示「仅检索」。保存后进入「密钥与调用记录」创建 API Key。[应用接入](http://10.10.4.171:30015/tet/knowledge-web/applications)

| 配置项 | 当前值或用途 |
| --- | --- |
| **应用 BaseUrl** | `http://10.10.4.140:31111`，当前禅道项目的业务网关。知识库用它生成返回的业务 API 地址，无需尾部斜杠。 |
| **MCP 连接地址** | `http://10.10.4.171:30015/tet/knowledge/api/mcp`，供 Codex 连接知识库。 |
| **Codex MCP 名称** | `company-knowledge`。从实际工单启动器使用的 Windows 账号及 Codex 配置读取。 |
| **认证变量** | `KNOWLEDGE_HUB_API_KEY`。配置到运行工单的 Windows 用户环境，启动器和阶段 CLI 从启动环境继承。更新变量后，通过新启动的进程验证。 |

[当前业务网关配置](../.agents/zentao-project.json) · [Windows 工单启动器](../.agents/skills/zentao-autodelivery/references/worker.md)

在新机器或新运行账号上，可用工单启动器所使用的 Codex CLI 登记同名 MCP。

```powershell
codex mcp add company-knowledge `
  --url 'http://10.10.4.171:30015/tet/knowledge/api/mcp' `
  --bearer-token-env-var KNOWLEDGE_HUB_API_KEY

codex mcp get company-knowledge
```

轮换时先创建新 Key，更新同名环境变量并从新的启动进程复验，再撤销旧 Key。曾经发到聊天中的 Key 应在正式运行前轮换。

## 实施状态与验收

| 检查 | 结果 |
| --- | --- |
| MCP 本机配置 | `company-knowledge` 已登记，Windows 用户环境已设置认证变量。 |
| 公司知识库读权限 | 实际调用 `search_knowledge` 和 `get_knowledge` 成功，读取到已发布的「查询离散点数据导入字段模板 API」。返回的业务网关与应用 BaseUrl 一致。 |
| Windows 运行环境 | Windows 阶段运行器监管的探针已用保存的凭据完成搜索和正文读取。用工单启动器同一 Codex 程序检查服务状态，确认 CLI 能发现上述两个工具。 |
| 流程规则 | 工单执行入口和阶段指引已加入查询规则，拆分与设计可按需使用。 |
| 完整阶段运行 | 阶段 Agent 的探针在首次工具调用前超时。真实工单中 `split.md`、`design.md` 的知识引用以及失败后继续拆分的行为待验收。 |

正式验收选一张确实需要核对现有能力或接口的测试工单。从实际 Windows 启动器运行，先核对材料评审只使用原单材料，再检查拆分和设计是否留下条目版本、实际决策和核验位置。另用隔离的测试配置模拟检索无结果或服务不可用，确认本地证据足够时阶段能继续，且只对仍缺关键证据的任务登记阻断。
