# 工单步骤和交付证据

使用工单配置快照中的步骤时限。每个时限都是单次尝试的最长耗时，从实际开始时起算，提前完成立即推进。记录每次尝试的开始、截止、结束和结论。失败后最多重试三次，重启沿用原尝试、原次数和原工单聊天。

## 按阶段安排验收

需求和 Bug 的材料评审、任务拆分和实施计划遵循[工单材料与流程冲突规则](../SKILL.md#工单材料与流程冲突)。主会话在派发阶段 Agent 时传递已核对的流程决定。设计或计划引用旧材料时，按同一规则处理其中的冲突。

拆分时把本地可验证的开发成果放入端内验收。镜像构建、推送、滚动更新和部署后业务复验属于后续阶段的交付检查，不列为本地验收必须通过的独立开发任务，也不作为本地验收的前置条件。计划明确各项检查的阶段和所需证据。部署后的业务复验以实际运行版本为准，记录真实业务结果。缺少对应环节、环境或数据时，在工单收尾中如实记录待验证事项。

## 新领取的工单

Story 的任务拆分、验收及交付状态记录在本地账本。相同拆分项跨修订保留编号，新增独立要求另用新编号。每端沿正常研发路径提交以下补充证据。

| 阶段 | 逐项证据 |
|---|---|
| 拆分 | `tasks.frontend`、`tasks.backend` 保留现有编号、描述、依赖及验收条件。跨端工单中需要页面联合验收才能交付的后端任务加 `"joint_acceptance": true`。 |
| 前端或后端计划 | 在原有 `applications` 或 `services` 之外，提供 `"task_repositories":{"F1":["app"],"F2":["app","shell"]}`。每项覆盖实际相关的全部本端仓库；跨端前端计划还列出需联合验收的后端任务对应的前端仓库。 |
| 服务验收或页面 E2E | 在原版本和 `verified_tasks` 字段之外，提供 `"task_results":{"F1":{"outcome":"passed","verification":"候选版本上的具体用例、观测结果或证据路径"}}`。结果为 `passed`、`failed` 或 `pending`。整步成功须覆盖本端所有任务；部分失败时分别记录能够独立核实的结果和受验版本。跨端页面验收同时提供实际交接的 `backend_versions`。需要联合验收的后端项也写入 `task_results`；联调发现后端拆分项未满足验收条件时，登记对应本地编号和失败证据。 |
| 逐仓合回 | 保留 `versions`、`merged_versions` 及现有最终内容复验要求。目标树有变化时，针对受影响任务补充 `"merged_task_verification":{"F1":"最终合回版本的用例及实际结果"}`。部分仓库成功时，失败回执也要列出已经实地读回的合回版本。 |

工单回执由本地账本分别核对任务对应的候选、验收结果和目标分支。返工时按最新候选版本更新本地任务状态和验收依据。

从本单 `attempt_start` 回执取实际步骤、角色和时限。证据保存在账本所在目录的 `items/<marker>/round-<run_round>/` 下。主会话负责派发、两端的分支核验与合回、交接和收尾。每个被选中的端由本端开发 Agent 负责设计到单测，由本端测试 Agent 独立审查与验收。纯后端工单只读取后端入口，纯前端工单只读取前端入口。

| 阶段 | 负责人 | 操作和成功证据 |
| --- | --- | --- |
| `material_check` | 主会话、评审 Agent | Story 先按[需求材料同步](#需求材料同步)同步仓库，再核对实际目录并提交 `evidence.path`，例如 `requirements/ZT-123/intent.md`，相对需求工作区。Bug 提交原单复现详情 `evidence.detail`，新 Bug 按[接单核对](#bug-接单核对)同时登记仓库和验收条件。账本解析材料正文并保留摘要和原标记。需求文件确实缺失时以 `failed` 和 `material_file_status:"missing"` 提交。 |
| `split` | 拆分 Agent | 项目单端设置决定实际范围。项目支持两端时优先用文档标记，缺标记再根据代码、接口与验收条件研判；双端配置中标记非法或矛盾时记录歧义。写 `split.md` 和结构化任务证据，格式见[账本命令](workflow-cli.md)。将超出范围的验收条件写入 `blockers`。 |
| `<端>.design`、`<端>.plan` | 本端开发 Agent | 按拆分清单在本轮的 `frontend/` 或 `backend/` 写 `design.md`、`plan.md`。设计附文件证据，计划登记非空且唯一的应用键数组 `applications` 或服务键数组 `services`。 |
| `<端>.branch_check` | 主会话 | 按[分支核验](branches.md)准备并实地核对每个目标仓库的 worktree，提交完整 `repositories`。 |
| `<端>.coding` | 本端开发 Agent、主会话 | 开发 Agent 在已核验工作树编辑、构建和测试，返回逐仓文件清单、原 HEAD、提交说明及验证证据。主会话通过统一 Git 入口执行 [candidate_commit](branches.md#编码与候选提交)，保留原 hooks，收到结果后把成功 `versions` 登记为候选。后端通过 service_runtime.py 运行服务配置的构建命令，跨端时编写联调文档。 |
| `<端>.unit_test` | 本端开发 Agent | 对有效 coding 的同一 `versions` 跑测试，以 `verification` 保存实际命令、结果和证据；不得自行提交。需要代码或生成文件修订时，失败结果传 `repair_required:true`，回到 coding 后重跑单测。 |
| `<端>.code_review` | 本端测试 Agent | 按[代码审查](#代码审查)逐仓检查基线到候选提交的差异，审查本端计划及候选改动。提交 `versions` 和 `verification`，记录位置、结论和严重度。 |
| `backend.acceptance`、`frontend.e2e` | 本端测试 Agent | 后端通过 service_runtime.py 启动指定服务并运行配置的 HTTP 检查，再按[后端服务验收](backend.md)运行用例。前端按[页面验收](e2e.md)启动本单版本的服务，复用测试浏览器的登录状态，核对浏览器加载的候选版本。提交 `versions`、`verification` 和逐项验证的本端任务编号数组 `verified_tasks`，覆盖当前有效清单。前端通过或代码返工须提交本轮 `agentlimb_receipt`。联合验收加 `backend_versions`，核对已交接服务版本。 |
| `<端>.integration` | 主会话、宿主执行器 | 通过统一 Git 入口执行 [integration_merge](branches.md#合回与恢复)，根据返回的逐仓结果继续。宿主处理快进、已包含及分叉，对已有暂存和未暂存改动分层核验。收到 `integration_conflict` 时按逐仓回执在当前阶段协调后重提。保存候选 `versions` 及已核验仓库的 `merged_versions`。旧路线最终树与候选不同时提交 `merged_verification`。启用合回后 E2E 的前端路线用实际合回 SHA 做页面验收。 |
| `backend.push`、`frontend.push` | 工单启动器和统一 Git 入口 | 工单快照启用 `runtime.git_push_enabled` 时，逐仓推送验收并合回的 SHA，即使该端没有镜像部署。部分交付依赖逐任务验收、实际合回及最终内容复验证据。核对快照、当前配置和分支核验回执，向配置分支普通推送并读回远端。已包含该 SHA 时登记已有远端版本。遇到分叉、权限或目标错误时记录该仓失败，保留其他仓结果。 |
| `backend.deploy` | 工单启动器和跨平台发布执行器 | 后端审查、独立验收、合回和已启用的 Git 推送成功后，按快照和当前授权选择实际服务的部署目标。用已合回版本打包并推送，按摘要更新 Deployment，核验 Pod 与网关版本后自动登记回执。工单主会话在此阶段交还执行权。详见[后端部署](backend.md#后端自动部署)。 |
| `frontend.deploy` | 工单启动器和前端部署 Agent | 核验前端 Git 远端已包含合回 SHA，从固定 SHA 打包并读回 Harbor 摘要。配置 Rancher 时继续更新并核验新 Ready Pod。详见[前端镜像发布](frontend-release.md)。 |
| `handoff` | 主会话 | 仅跨端运行。后端合回后读取联调文档、独立验收和实际环境版本，提交[交接证据](backend.md)。交接失败后记录依赖交接的任务，按账本继续独立的前端任务。 |

端内返工依次完成修复、单测、复审或重验。联合验收发现后端缺陷时注明责任端，按同一尝试中账本返回的分段修复并再次交接，使用新版本跑受影响的联合验收。涉及任务或接口约定变化时，按阶段回执指定的角色更新范围并说明依据。主会话收尾以有效版本、实际验收和所有必需任务为准；安全合回成功的事实与未解决的验收项分别记账。

编码、单测、审查和验收登记成功时，账本会读回工单工作树的 HEAD、已跟踪文件和暂存区。单测发现需要修订时，普通单测失败的 `repair_required:true` 生成同端 coding→verify 序列；返工中单测失败则回到紧邻的同端 coding，保留此前有效历史。新 coding 回执使旧版本的下游证据失效，单测、审查和验收按新 SHA 重跑。跨轮恢复先复核保留的历史。hooks 自动改文件、提交后检查失败或回执丢失按[候选恢复](branches.md#编码与候选提交)处理，不能直接登记旧版本成功。主工作区中用户已有的改动须保留。

### Bug 接单核对

领取快照开启 `runtime.streamlined_bug_intake` 的 Bug 由主会话直接执行 `material_check`。按接单回执确认本轮执行角色。省略独立材料评审、拆分、设计和计划，复用现有的分支准备、编码、单测、独立审查、验收、合回和发布。已领取的工单按原配置快照执行。

- 成功回执填写 `detail`（原 Bug 的复现、预期和实际结果）、`repositories`（按 `frontend` 或 `backend` 列出配置中的应用键或服务键）和 `acceptance`（可复验的条件数组）。例如，前端仓库清单为 `{"frontend":["tet-smart-log"]}`。无法确认所需材料或目标仓库时，以实际失败或阻断及证据登记。
- 跨端回执填写 `interface_contract`。存在前端对后端的依赖时填写 `depends_on_backend:true`，可独立交付时填写 `false`。省略时按存在依赖处理。每端验收项有差异时，用 `acceptance.frontend`、`acceptance.backend` 分别登记数组。账本生成对应的 `frontend`、`backend` 验收编号，后续回执仍用该端有效任务编号及实际版本。
- 开发 Agent 在修复记录中写明根因和影响范围。返工中需要修订契约时，账本保留原有修订分段，由主会话用同一接单格式更新仓库和验收范围，随后重新核验受影响的工作树。

## 代码审查

测试 Agent 逐仓核对分支基线、候选提交和单测版本，审查 `git diff <base> <candidate>`。根据材料、计划和验收条件保存覆盖范围、具体缺陷和对应提交号。返工后对新的候选 SHA 重新核验，回执登记 `versions` 和 `verification`。

## 公司知识库查询

材料评审使用工单材料。材料评审通过后，拆分 Agent 在现有能力、应用归属或跨应用依赖需要确认时查询公司 MCP `company-knowledge`。按功能名、业务对象或页面入口调用 `search_knowledge`，用命中条目的 `itemId` 和 `versionId` 调用 `get_knowledge`。在 `split.md` 记录引用、发布状态和它影响的拆分决定。研发范围仍按项目配置和工单材料确定。

设计 Agent 先读 `split.md` 的引用。需要补充共享组件、接口或上游依赖的证据时，再查原文或用 `traverse_knowledge` 查关系。在实际目标仓库验证源码或接口，在 `design.md` 记录采用的结论和核验位置。独立验收沿用已记录的引用，并以候选版本上的实际验证为准。

无命中、鉴权失败或调用超时时，在当前阶段时限内记下原因，继续检查工单材料、源码和实际接口。只有关键条件仍无法核实才按现有规则记录受影响任务。使用与当前任务相关的最少查询信息，交付文档只保存所用条目的引用和结论。API Key 由启动环境通过 `KNOWLEDGE_HUB_API_KEY` 提供。

## 需求材料同步与本地评审

Story 的材料检查在同步后的需求仓库提交上执行，保存分支、上游、SHA 和材料路径。按账本返回的 `material_sync` 入口申请同步，成功后检查该提交的材料。链路错误按同步失败处理。评审中的需求材料齐全就直接拆分；文件缺失或有明确的关键缺项时，记录具体原因，以「待补材料」收尾并在原需求备注。Bug 继续按接单核对流程验证复现条件。

## 超时和受控停止

1. 开始每次尝试前，在对应工具中确认能够按时限停止执行。登记实际 Agent 或工具会话及其启动的受控进程归属。进程身份至少核对 PID、启动时间和所属尝试，保留启动工作区或等效证据。
2. 到达截止时间后停止本次执行。中断 Agent 或返回工具超时只说明该层停止请求，另核对本次启动的进程树。必要时使用已验证的受控进程停止手段，只结束归属于本次尝试的进程，保留用户原有服务。记录 Agent 状态、进程退出或有效隔离的核验结果。
3. 确认停止或有效隔离后才允许重试或释放执行名额。执行环境缺少可靠停止能力时记录阻断证据。停止与隔离均未获证实时保留名额并继续对账，待写回等独立事项可以继续推进。

不得将时间预算、Agent 中断回执、shell 会话退出和进程树退出混作同一份证据。保存结果前核对本次尝试仍有效。迟到的结果只关联原尝试，避免推进当前步骤。
